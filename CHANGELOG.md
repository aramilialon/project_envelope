# Changelog

All notable changes to envelope are listed here, newest first. Versions follow semantic versioning: 1.0.0 marks the whole product (budget, portfolio, mobile and everything else in `docs/design.md`), so every 0.x.y release is still pre-1.0 by design, however usable a given 0.x.0 milestone group already is on its own. A new minor version (0.x.0) starts a milestone group (Budget, Portfolio, Mobile, ...); each patch release (0.x.y) closes one milestone within that group.

Each entry groups changes under **Added**, **Changed**, **Fixed** and **Removed**. Changes not released yet are one file each in [`changes/unreleased/`](changes/unreleased/README.md), compiled into this file at each release.

## [Unreleased]

### Added

- `apps/api`: a transaction's date can be edited (`#655`): `PATCH .../accounts/:accountId/transactions/:transactionId` takes `occurredAt` (`YYYY-MM-DD`), dated at midnight in the workspace's time zone as on create, so the transaction moves to the budget month of its new date. Both legs of a transfer move together, and a cleared other leg goes back to uncleared. A trade's cash leg keeps the trade's date (409 `trade_owned_transaction`). `amountCents` alone now changes the amount of a transaction that has one split, keeping its category and memo (the other leg of a transfer follows); on one with several splits it is refused with `amount_needs_splits` until the splits come with it.

### Fixed

- `apps/api`: editing a transaction no longer ignores what it cannot use (`#655`). A field it does not take, `accountId` and ids included, is refused with 400 `unknown_field` naming the field; a field of the wrong type, or a status that is not `pending`, `cleared` or `reconciled`, with 400 `invalid_field`; a body that is not a JSON object with 400 `invalid_body`. Editing or deleting a transaction through an account that does not hold it answers 404. Creating a transaction or a transfer on a date that does not exist (`2026-02-30`, `2026-02-29`) or is not written `YYYY-MM-DD` (`2026-1-5`, `not-a-date`) is refused with 400 `invalid_date` instead of a server error, and any such date that reaches the database answers 400 `invalid_date` too.

## [0.2.0] - 2026-11-21

### Added

- `apps/api`, `apps/web`: rate limits (`#566`, [ADR 0017](docs/adr/0017-api-rate-limiting.md)). Per client address, before authentication and on every route, the health check included (2400 requests a minute by default), and per signed-in user after it (1200 requests, 120 writes and 10 file imports a minute by default, sized from an ordinary web session of about 325 requests in 7 seconds; the per-address limit stays above the per-user one because one address can carry a whole household), all configurable by environment. CORS preflights are not counted, and `Retry-After` is exposed to the web app. A request over a limit is answered 429 `too_many_requests` with `Retry-After`; the web app says how long to wait where it saves a transaction, moves money, imports a file or reconciles. `TRUST_PROXY` names the reverse proxies whose `X-Forwarded-For` is believed (none by default; behind Caddy it must be `127.0.0.1`, or the whole household is counted as one address). Sign-in stays limited by Keycloak's own brute-force detection.
- `apps/web`: a screen whose load the API refuses over its rate limit (`#683`) says how long to wait instead of its "could not load" error, and loads again on its own once the wait is over (waiting at most a minute, twice at most); saves still only say how long to wait and are never retried on their own.
- `apps/api`, `apps/web`: a `brokerage` account type (`#74`), always off budget — the portfolio connects to the budget through off-budget accounts, so money paid to the broker is a transfer from an on-budget account to an off-budget one, which carries a category on its on-budget leg (`#378`): the investment is spending from that category, planned as an envelope. Creating one without `onBudget` defaults it to off budget; asking for it on budget is refused with the stable code `brokerage_on_budget`, and migration 0025's `CHECK` constraint enforces the same in the database. The "Add account" form lists it ("Brokerage" / "Conto titoli") with no "On budget" choice.
- `apps/api`: portfolios (`#75`) — a `portfolios` table (migration 0027, workspace-scoped with Row-Level Security) and `/workspaces/:workspaceId/portfolios` endpoints to list, get, create, rename, change the free-text purpose of, archive, unarchive and delete a portfolio. Names are unique per workspace among non-archived portfolios, ignoring case and surrounding spaces (409 `name_taken`). A portfolio declares no accounts: the accounts it spans will come from its trades (`#77`).
- `@envelope/core`: positions computed from trades (`#78`): `computePositions` replays every trade of an instrument in the workspace, across accounts, in the fixed order `(trade date, split first, occurredAt, createdAt, id)` (a split on its ex-date) and returns the quantity, the cost in cents, the average cost (display only, shared by every portfolio of the account) and realized gains per account and instrument, and per portfolio its quantity, its share of the cost (largest remainder, adding up exactly) and its realized gains, with trade, income and transfer fees, transaction taxes, accrued interest paid and received, gain tax withheld (`gainTaxWithheldCents`), gain tax adjustments as entered, a refund positive (`gainTaxAdjustmentsCents`), the tax on a managed account's result, a tax on gains rather than a cost (`managedResultTaxCents`), gross dividends and coupons (`incomeGrossCents`), withholdings and standalone fees and taxes (stamp duty and other taxes) as separate totals. The cost follows the Italian rules: fees are part of it, the financial transaction tax and accrued interest are not; a transfer between two accounts carries the cost the source removes (so a backdated trade in the source flows through), a transfer from outside the app brings its own cost, transfers between portfolios of the same account move quantity only, splits leave the cost unchanged and need a row for every portfolio holding the instrument, in every account. Every trade is checked against its type: unused amounts must be 0, amounts cannot be negative except a gain tax adjustment (extra tax charged), timestamps must be strict ISO 8601 with an offset, transfer legs must match, in accounts of the same currency, and split rows of one instrument on one date must share one ratio in every account. `validatePositionHistory` and `applyTradeChanges` let the API check a history after an insert, edit or delete, with the stable codes `insufficient_quantity`, `split_missing_for_portfolio`, `split_ratio_mismatch`, `split_duplicate`, `split_leaves_no_quantity`, `invalid_trade` and `unknown_trade`; `valuePosition`, `summarizeByPortfolio`, `summarizeByAccount` and `derivedResults` (income, costs and taxes on gains from a position's or a summary's totals) complete it. The domain guide gains the replay order, the definitions of income, costs, taxes on gains and net result, and the worked examples; ADR 0011 gains the trade date in the replay order.
- `@envelope/core`: quantities and prices of financial instruments as scaled integers (`#73`, ADR 0011): `Quantity` (units × 10^8), `Price` (× 10^6) and `PriceFactor`, with validation, locale-aware parsing (an Italian decimal comma included) and exact formatting, plus `amountOf`, `quantityFor`, `priceFrom` and `proportionalCost`, each with its own rounding rule and exact beyond 2^53. Docs: ADR 0011 decides the `quantity_e8`/`price_e6`/`price_factor_e6` columns, the `quantityE8`/`priceE6`/`priceFactorE6` API and sync fields, the rounding rules and the fixed replay order of trades; the glossary and the domain guide gain quantity, price, price factor and nominal, with worked examples.
- `apps/api`: a shared instruments catalog (`#76`, migration 0026): `POST /instruments`, `GET /instruments?q=` and `GET /instruments/:instrumentId`, open to any signed-in user. An instrument is a listing, identified by an ISIN (check digit verified) or a ticker on an exchange (the exchange's 4-character ISO 10383 MIC, such as `XMIL`), with a type that keeps tax-relevant distinctions apart (`stock`, `fund` with ETFs included, `etc_etn`, `government_bond`, `bond`, `certificate`, `cash`, `other`); the same listing cannot be added twice, and a search needs an exact ISIN or a prefix of at least 2 characters, returning at most 20 results. Instruments cannot be updated or deleted through the API; `apps/api/README.md` ("Administration") shows how an administrator corrects the catalog with SQL. Responses never say who added an instrument or when. A `priceFactorE6` (the factor scaled by 10^6, [ADR 0011](docs/adr/0011-quantities-and-prices-as-scaled-integers.md), for example `10000` for 0.01, a bond quoted in percent of nominal) records how a price turns into an amount. Private instruments, with no ISIN and no ticker (real estate, a company pension fund), are not supported yet; they are planned for milestone 0.2.1 (`#505`).
- `@envelope/core`: `isValidIsin`/`assertIsin`/`isinCheckDigit` (ISIN check digit), `normalizeInstrument` (validation and normalization of a new instrument, with stable `ValidationError` codes; its price factor is `#73`'s `PriceFactor`) and `parseInstrumentSearch` (`#76`).
- `apps/api`, `apps/web`, `@envelope/core`: the tax regime of brokerage accounts (`#508`). A workspace has an optional tax country, set by its owner with `PATCH /workspaces/:workspaceId` and listed by `GET /me/workspaces`. A brokerage account records whether the broker is an Italian withholding agent — fixed per account, set once with `PATCH .../accounts/:accountId` on an account that has none — and a history of tax regimes: self-declared, administered or managed. The first period may start on any date (by default the day it is recorded) and also applies to every earlier date; every later one starts on 1 January. A trade uses the regime in force on its own date, so a change from a later 1 January does not alter trades dated before it; recording or correcting the history re-reads the trades it covers (`GET`/`POST`/`PUT .../accounts/:accountId/tax-regimes`, `PUT` replacing the whole history in one transaction). In an `IT` workspace a new brokerage account needs both (`tax_regime_required`); an administered or managed regime needs the flag set to true (`tax_regime_requires_withholding_agent`); other account types, and workspaces whose tax country is not `IT`, refuse them (`tax_regime_not_applicable`). Brokerage accounts created before the tax country was set keep working with no regime until one is added. `@envelope/core` gains `regimeAt`, `validateTaxRegimeHistory`, `validateAccountTaxSettings`, `validateTaxRegimeChange` and `validateWithholdingAgentChange`; migration 0028 adds the columns and the `account_tax_regimes` table, with Row-Level Security and a trigger enforcing the same rules. In an `IT` workspace, the "Add account" form asks a brokerage account's regime ("Regime fiscale": Dichiarativo, Amministrato, Gestito, each with a one-line hint) and, for a self-declared one, whether "Il broker è un sostituto d'imposta italiano"; its checkboxes and fields now reach 44px. No screen sets the tax country or shows the history yet (`#516`): both are API-only. No tax is computed yet.
- `apps/api`, `@envelope/core`: trades (`#77`, ADR 0012). A `trades` table (migration 0030, workspace-scoped with Row-Level Security, one `CHECK` per type) and `GET`/`POST /workspaces/:workspaceId/trades`: record a buy, sell, dividend or coupon, fee or tax on a brokerage account, filed under a portfolio; a transfer of securities in one request (both legs, between two portfolios of an account or between two accounts, or one leg from or to outside the app); and a split, entered once and recorded for every portfolio holding the instrument, in every account. List them filtered by portfolio, account or instrument. A trade is refused when it would make a portfolio's holding negative at any date (`insufficient_quantity`), when a backdated trade would leave a portfolio without its split row (`split_missing_for_portfolio`), when the account is not a brokerage account or the instrument is in another currency, and when its amounts break the rules for its type, the instrument or, in an `IT` workspace, the account's tax regime on the trade date; the broker's figures are never compared with an estimate. Every trade that moves cash writes its cash leg, a transaction on the same account (positive when cash comes in), uncleared and dated on the trade date until it shows on the broker's statement: its amount, account and date come from the trade and cannot be changed or deleted through the transactions API (`trade_owned_transaction`) or sync; its memo, payee and status can. A portfolio with trades can no longer be deleted (`portfolio_has_trades`).
- `apps/api`: positions (`#79`): `GET /workspaces/:workspaceId/portfolios/:portfolioId/positions` and `GET /workspaces/:workspaceId/accounts/:accountId/positions`, readable by every member, rebuilt from the trades on every request. Each position, per account and instrument, carries the instrument's catalog fields, the quantity, the cost, the account's average cost (in the instrument's price unit, so a bond's is in percent of nominal; shared by every portfolio of the account, for display only), the realized gain and, as separate totals, trade, income and transfer fees, the financial transaction tax, accrued interest paid and received, gain tax withheld, gain tax adjustments, managed result tax, gross dividends and coupons, foreign and domestic withholdings, and standalone fees and taxes, plus the income, costs and taxes on gains worked out from them; a summary per currency adds the fees and taxes recorded without an instrument. A portfolio gets its own quantity and realized gain and its share of the account's cost, worked out from the whole history of each instrument in the workspace, other portfolios and accounts included. An archived portfolio's positions are still readable; another workspace's portfolio or account is a 404. No prices exist yet, so there is no current value, no unrealized gain and no net result (milestone 0.2.1).
- `apps/api`: edit and delete trades (`#509`, ADR 0012) with `PATCH` and `DELETE /workspaces/:workspaceId/trades/:tradeId`. A transfer's two legs, and every row of a split, are edited or deleted together, through any of their ids; a trade's type cannot change. Editing rewrites the trade's cash leg in the same transaction, keeping its memo and payee; a cleared leg whose amount, account or date changes goes back to uncleared. An edit of a buy or a sell that changes the quantity, the price or the instrument without a gross computes the gross again, so the broker's figure must be sent again to keep it. A trade's create and edit requests now refuse a field they do not know (a plain 400) instead of ignoring it. The leg is created when the trade starts moving cash, deleted when it stops, and moves with the trade to another account. Deleting a trade deletes its cash leg. Every edit or delete is checked against the workspace's whole history of the instrument, in every account, and refused when it would make a portfolio's holding negative at any date (`insufficient_quantity`): deleting an old buy that a later sale depends on, backdating a sale, making a buy smaller or moving it to another account, portfolio or instrument. The checks for a new trade (account, portfolio, instrument, amounts, tax regime) apply to the edited trade too. A trade whose cash leg is reconciled cannot be edited or deleted until the reconciliation is unlocked (409 `reconciled`), and in sync a change to a trade's fields is refused on the same condition. Both are written to the audit log. An edit that changes nothing, or a body that is not a JSON object, is refused with a 400; an edit that loses a race with another request moving the same trade to another instrument answers 409 `concurrent_change` and can be retried. Migration 0031 grants the database role the deletes and the updates of the columns an edit writes (never a trade's id, workspace, type, transfer link or creation time), and makes a cash leg follow its trade to another account. The workspace id of a request is now handled in lower case whatever the case it was sent in, so two requests naming the same workspace in different cases cannot take different locks.
- `apps/api`: a real-process smoke test for milestone 0.2.0 Portfolio schema & instruments (`#503`, ADR 0007), `src/smoke/0.2.0-portfolio.smoke.test.ts`: a mixed household driven over HTTP from its budget to its portfolios — an "Investments" category funding an off-budget, administered brokerage account in an `IT` workspace; buys in two portfolios, a sale with gain tax, a dividend with foreign and domestic withholding, a split covering both portfolios, a transfer of units between them, a government bond bought with accrued interest, a custody fee, an edit and a delete. Its positions per portfolio and per account, their income, costs and taxes on gains, and the broker's cash are checked against values worked out by hand; so are the budget month, which the trades leave untouched, and its invariant. It also proves that a reconciled cash leg locks its trade, that a `read_only` member can read but not write, and that another workspace sees none of it.
- Development: disposable environments for exploratory and end-to-end runs (`#536`). `pnpm --filter @envelope/scripts explore:up` creates a database `envelope_explore_<run>` and a Keycloak realm `envelope-explore-<run>`, migrates the database, starts the API and a production build of the web app on free `127.0.0.1` ports with matching issuer, origin, `VITE_*` and queue settings, and creates the `household`, `investor` and `mixed` personas (each owning a workspace created through the API, plus an editor and a read-only member) with random passwords; it writes a manifest with the URLs, usernames, passwords and workspace ids, never a superuser, database role or Keycloak admin credential. The databases live on a PostgreSQL server of their own, never the shared development one: a container the tool manages (`envelope-explore-postgres` on `127.0.0.1:55432`, its superuser password generated into `~/.config/envelope-explore/` and passed as `POSTGRES_PASSWORD_FILE`), or `EXPLORE_DATABASE_URL` in CI; port 5432 and any server holding the `envelope` or `keycloak` database are refused. Each run's API logs in as two roles of its own that may connect to its database only, so a run's credentials open nothing else. `explore:down <run | manifest>` stops the processes, drops the database and deletes the realm, and can run twice; Ctrl-C or SIGTERM during `up` removes what it created; `explore:sweep` removes leftovers older than 24 hours. Any name without the exact prefix, and the `envelope` and `keycloak` names, are refused. `scripts/keycloak/bootstrap.sh` takes `ENVELOPE_BOOTSTRAP_REALM` and `ENVELOPE_BOOTSTRAP_WEB_ORIGINS` (only `envelope` or a disposable realm; plain origins only, never for the shared realm) and no longer puts the admin password or token on a command line. The Playwright suite runs against an environment when `E2E_MANIFEST` points at its manifest, and a new CI job, `e2e`, does so on every push and pull request, non-blocking for now; CI also runs the scripts' own unit tests.
- Docs: the portfolio API reference (`docs/portfolio-api.md`, `#81`) — recording a portfolio through the API with no screens yet: the schema (Row-Level Security, composite workspace keys, the scaled integers `quantity_e8`, `price_e6` and `price_factor_e6`), every portfolio endpoint with its role, bodies and validation codes, the replay order, cash legs, edits and deletes, retries with client ids, positions and their income, costs and taxes on gains, and a worked example in integer minor units. The domain guide gains how a transfer to an off-budget account takes a category, and what each Italian tax regime changes in the trades, with worked examples; the glossary gains the portfolio terms.

- `apps/api`: a seeded model-based random walk through the API (`#80`, ADR 0013), run with the integration tests. Three workspaces — a household that only budgets, an investor who only invests, and a mixed household that does both, each with an owner, an editor and a read-only member — take hundreds of interleaved steps: accounts, transactions, transfers between the budget and the broker, reconciliation, portfolios, trades of every type, their edits and deletes, a trade's cash leg changed through the transactions API or sync, and requests naming another workspace's ids. After every step the API's answers are checked against `@envelope/core` applied to what the API accepted (positions, summaries, cash legs, budget months) and against invariants that need no model (the budget invariant, a transfer's legs, a brokerage account's balance and its identity); a refused request must carry a known code and change no row of any workspace, and no workspace may reach another's rows. CI walks 2 fixed seeds × 300 steps in-process, checks that one seed walks the same way twice, and walks 60 steps through the real server; every accepted answer is first checked to have kept every field the request sent; `WALK_SEED`, `WALK_STEPS`, `WALK_DRIVER=fetch` and `WALK_REPLAY` run longer walks and replay a failure's operation log (`apps/api/README.md`, "The random walk"). The fixed-seed generator the randomized tests use now lives in one place, `@envelope/core/testing`.

### Changed

- `apps/web`, `packages/i18n`: interface languages are a list, not a pair (`#620`). The shipped languages are a data file, `packages/i18n/locales/index.json`, read by locale negotiation (`resolveLanguage`, now in `packages/i18n` and the same for every platform) and by the completeness check; a catalog that is not listed there is never offered and never checked. The web app downloads only the catalog of the language it shows, before the first render, from a chunk of its own that the service worker precaches, and the page's `<html lang>` now follows that language. The completeness check moves out of `pnpm test` into `pnpm --filter @envelope/i18n check`, covers every shipped catalog and requires an `other` branch in every plural and select; CI also checks that the extraction leaves `en.json` unchanged. The extraction moves to `pnpm --filter @envelope/i18n extract` (`pnpm --filter @envelope/web i18n:extract` still works). Push notifications fall back to English, explicitly, for every language other than English and Italian. New tests format amounts in German, Spanish and French.
- `apps/api`: an archived portfolio takes no new trades (`#597`). A buy, sell, dividend, fee or tax filed under it, and a transfer of securities into it, are refused with a 400 `portfolio_archived` and `details.portfolioId`; so is an edit that moves a trade or a transfer's leg into an archived portfolio. The trades it already has stay editable and deletable, a transfer out of it is allowed so it can be emptied without unarchiving it, a split still writes its row there (a split is a fact about the instrument, so an archived holder never blocks it), and unarchiving it lets it take trades again.
- `apps/web`, `apps/api`, `@envelope/core`: the transaction form records money coming back from an off-budget account as money to assign (`#599`). A transfer now goes "To another account" or comes "From another account" ("Verso un altro conto" / "Da un altro conto"); switching direction keeps the account chosen, and "From account" does not list credit cards. Off-budget accounts are marked "(off budget)" in the account list. Coming in from an off-budget account (a broker, a loan) to a cash account, the category select offers "Unassigned (€X)" first, selected by default, then the categories, and a hint says how much "Unassigned" or the chosen category goes from and to in the month of the transfer's date ("I soldi entrano nel budget: «Da assegnare» passa da X a Y."); "Unassigned" sends no category. Into an on-budget credit card, and going out to an off-budget account, a category is still required. Editing such a transfer's on-budget leg can now set its category or clear it back to "Unassigned" (a category-only change, the other leg left alone). The register row of a transfer with an off-budget account reads "Transfer · From <account> · Unassigned" (or the category), and "Transfer · To <account> · <category>" going out. The import's check step follows the same rule for a row marked "Transfer from …"/"Transfer to …" an off-budget account. Every transaction the API returns now carries `transferAccountId`, the account of a transfer's other leg (null otherwise), and `@envelope/core` gains `transferCategoryRule` and `availableAfterInflow`, the rule and the hint's figures the form and the import share. On a phone, a side sheet (this form among them) now covers the whole screen above the tab bar, which used to hide its buttons; the Outflow/Inflow/Transfer and direction toggles show a focus ring; a split left on no longer hides a transfer's category; and the form's title and buttons are translated ("Nuova transazione", "Modifica transazione", "Aggiungi", "Salva").
- `@envelope/core`, `apps/api`: money coming back from an off-budget account lands as money to assign (`#598`). The on-budget leg of a transfer from an off-budget account (a broker, savings kept apart, a loan or mortgage) into a cash account may now be left without a category: it is then income to assign ("Unassigned") in the month of its date, like a salary; a real category can still be chosen, for example to refill the envelope that funded the investment. `POST .../transfers` and the import's transfer confirmation accept such a transfer without `categoryId`, and editing its leg can clear or set the category; a category-only edit leaves the other leg, and its status, alone. A transfer from an off-budget account into an on-budget credit card still needs a category (`card_income_not_supported`, with `details.accountId`), and so does a transfer to an off-budget account (`uncategorized_transaction`), on create and edit. In `@envelope/core`, `aggregateTransactions` counts that leg as income, and refuses an outgoing leg in `UNASSIGNED` as `uncategorized_transaction`. The web app offers it since `#599`. The domain guide's "Money moved to an off-budget account" gains the rules for money coming back, with worked examples; the portfolio API reference says how to take money back out of the broker.
- Documentation: every reference screenshot in `docs/ux/screenshots/` now exists in a light and a dark version (`<name>-light.png`, `<name>-dark.png`), and the README's gallery shows the one matching the reader's theme with `<picture>`; the hero is a diagonal light/dark split of the budget month (`budget-month-split.png`) and the phones a light, dark, light row (`phones-mixed.png`). The real-app screenshots were retaken over the demo workspace in a disposable environment, the phones from the current mockups with the budget month's running-total line instead of the old bar timeline (`#391`). `scripts/screenshot-mockups.ts` (`pnpm screenshots:mockups`) renders the mockup screenshots and the mixed images; `scripts/screenshot-demo.ts` now also shoots sign-in, the workspace picker and reconciliation, and it and `seed-demo.ts` can target a disposable environment (`KEYCLOAK_REALM`, `WEB_URL`; `seed-demo.ts --second-workspace`). The rule is written in `docs/design.md`, `docs/ux/README.md`, `scripts/README.md` and the UX reviewer's checklist (`#587`).
- Dependencies: the open security alerts on the lockfile are resolved (`#540`). `apps/api` moves to `fastify` 5.12.8 (header validation bypass) and, through it, takes the patched `fast-uri` 4.2.3 (under `@fastify/ajv-compiler` and `fast-json-stringify`) and 3.1.9 (under `ajv`), both API runtime code; `apps/web` moves to `vite` 8.3.8 (dev server file access and `launch-editor` fixes) and `vitest` 5.1.1, which no longer installs `@vitest/ui`. The lockfile also takes the patched `undici` 8.13.0 (under `jsdom`, tests only) and `serialize-javascript` 7.1.4 (under the PWA build, build time only). The `fast-uri`, `undici` and `serialize-javascript` versions are all within the ranges their parents already allow. The root `package.json` overrides `glob` to 14 under `workbox-build`, which brings `minimatch` 11, because no release of `workbox-build` pulls the patched versions yet; the README's "Dependency overrides" section explains it. `pnpm audit` reports no known vulnerabilities.
- `apps/api`: the integration and smoke tests are safe to run in parallel on one machine, each run against a database of its own (`#519`). The test Keycloak realm's access tokens live 60 seconds instead of 3, and the two tests of expiry ask for a 2-second token on purpose; a 5xx from Keycloak's admin or token endpoint, which concurrent runs creating and deleting realms occasionally get, is retried a few times; the tests no longer change the `envelope_app`/`envelope_queue` passwords (they log in with roles of their own, `#585`), so a test run no longer breaks a dev server and `scripts/dev/reset-role-passwords.sh` is only needed to repair a server; the smoke tests start the server on port 0 and read the port it bound from one `{"msg":"listening",…}` line the server now prints whatever `LOG_LEVEL` is, instead of fixed ports 3901 to 3906 (`PORT=0` is accepted outside production, and a `PORT` that is not plain digits, an empty one included, is refused); and the tests of the `scheduled-transactions-fire` job, which fires every workspace in its database, run in a throwaway database of their own, so workspaces other test files left behind cannot break them.
- `apps/api`: the tests never change the login or password of `envelope_app`/`envelope_queue` any more (`#585`). Each test database gets two login roles of its own, members of those two, whose names and passwords are derived from `DATABASE_URL` (which must therefore include the superuser's password); a run whose database is dropped leaves its roles to the next run, which drops them. Before, a run from a checkout with another password source changed those cluster-wide passwords, and a real server another run had started answered 500 when it opened a new connection. A real-process test that fails now prints the server's own output, and the smoke tests' servers log warnings and errors instead of fatal errors only

### Fixed

- `apps/api`: a trade written to a closed account is refused with 409 `account_closed` whatever it does (`#741`). Editing a sale's quantity or date, deleting a buy a later sale needs, or adding a sale or a transfer out of a closed account answered 400 `insufficient_quantity` (or `split_missing_for_portfolio`), because the position replay ran before the write reached the database's guard; the account is now checked first, in the same transaction. A sale beyond the holdings of an open account still answers `insufficient_quantity`. A close refused because a scheduled transaction uses the account now names the one due first: `account_not_empty`'s `details.scheduled` carries `scheduledTransactionId` and `nextDueDate` (the earliest next due date, `null` when none) beside `count`.
- `apps/web`: a write refused because an account is closed now says so everywhere (`#741`). On a closed account's register, reached by its address, changing a transaction's status, "Mark", "Record" and "Unlock" showed nothing at all when the API refused them; they now say the account is closed, and any other failure says the action failed. ## [0.1.6] - 2026-09-30

### Added

- `@envelope/core`: a hybrid logical clock (HLC) — `nextHlc` ticks a device's own clock forward even if its wall clock disagrees with or runs behind a previous value, `compareHlc` gives any two changes a total, deterministic order, the basis for the sync protocol's "last write wins" (design.md, "Field-level change protocol") (`#42`).
- `apps/api`: `change_log`, one row per field-level change (entity id, field name, HLC, device id, value); `recordChange` is idempotent on the change's own id, so a repeated network retry never creates a duplicate row; `getLatestChange` reads the current winner for one entity's field (`#42`).
- `apps/api`: `POST /workspaces/:workspaceId/changes` applies a device's own queued field changes, converging to the change with the later clock regardless of arrival order, through an explicit allowlist of supported fields (`transactions.memo`/`transactions.payee` for now) rather than building `UPDATE` SQL from the device-supplied field name directly (`#43`).
- `apps/api`: two offline devices independently undoing the same assignment-ledger row no longer surfaces as a raw error on the one that syncs second — recognized as "already undone by the other device" and dropped silently, the same outcome as undoing an already-undone row through the existing API (`#43`).
- `apps/api`: `GET /workspaces/:workspaceId/changes` — the download side of the sync protocol: every field-level change later than the clock a device last saw, or all of them for a first sync, ordered the same way `compareHlc` would; a read-only member can call it, unlike the upload side (`#44`).
- `apps/api`: an incoming field-level change to a reconciled transaction is now rejected outright (`"locked"`), design.md's "the server rejects later changes" — checked before clock resolution even runs, and never recorded, so a retry after the transaction unlocks (`#32`) is unaffected by the rejected attempt (`#45`).
- `apps/api`: 0.1.6's checkpoint smoke test against the real process (ADR 0007) — two simulated devices, each with its own HLC and offline queue, make offline edits including a genuine conflict on the same field; syncing converges both to the same result, the later clock wins the conflict, neither device's own non-conflicting edit is lost, and a resent change never creates a duplicate `change_log` row (`#46`).

## [0.1.5] - 2026-09-30

### Added

- `apps/api`: the queue module's `QueueDriver` interface (`enqueue`, `schedule`, `work`) and its `postgres` adapter (pg-boss), the only file allowed to import it (design.md, "Queue module"). Every queue it creates uses the `exclusive` policy, so a repeat `deduplicationKey` is rejected instead of merely recorded; `enqueue` accepts the caller's own transaction client, so the job commits or rolls back with the data that triggered it, pg-boss's own job table doubling as the outbox. A new `envelope_queue` role (its own migration) gives pg-boss the schema-management privilege `envelope_app` deliberately does not have, without widening the running server's own connection (`#34`).
- `apps/api`: the queue module wired into `main.ts`, and into `createTransaction`/`createTransfer` — creating a transaction or a transfer now queues a `budget-recompute` job in the same database transaction, deduplicated per workspace and month; a job written inside a transaction that later rolls back is never delivered. `envelope_app` is granted `SELECT`/`INSERT` on pg-boss's own tables, present and future, so it can write that job through its own connection without the `CREATE` privilege only `envelope_queue` holds (`#35`).
- `apps/api`: `processed_jobs`, so every job delivery is idempotent without the job author having to check it — `work` opens its own transaction, sweeps rows past the 30-day retention, inserts the job's id, then runs the handler; a repeat delivery's insert hits the unique constraint, is rolled back, and the handler never runs (`#36`).
- `apps/api`: push notification delivery — a `PushDriver` interface, a real `web` adapter (Web Push, VAPID), and `ios`/`android` stubs deferred to the mobile app (`0.3.0`). A device's own token lives in `device_tokens`, scoped by user rather than workspace; `sendPushToUser` sends to every one of a user's devices, recording each as a `notification_deliveries` row and resuming only from the still-pending ones on a retry. The triggering job's id doubles as the Web Push `topic`, so a duplicate delivery replaces rather than duplicates a still-pending notification on the device (`#39`).
- `apps/api`: the `budget-recompute` job now actually runs — the first real `work()` handler registered in the codebase. It recomputes a workspace/month's budget problems (a negative category, a purchase exceeding the available balance, money to assign) and notifies every workspace member, regardless of role, only when a problem is new or its amount has changed since the last time (`notified_budget_problems`), not every time the job happens to run while it persists unchanged. Notification text is a small, self-contained English/Italian lookup local to `apps/api` (no catalog infrastructure exists yet; the i18n library is chosen in phase 1), picked by the recipient's own `language`, with amounts formatted in their own `locale` (`#40`).
- `apps/api`: the shared double-delivery test harness (design.md, "Queue module") — every registered job type must prove that redelivering the same job id produces its effects exactly once; a job type with no case fails the harness's own coverage check (`#37`).
- Docs: a how-to guide for self-hosting push notifications — generating a VAPID key pair for the `web` adapter, and why `ios`/`android` have nothing to configure yet (`#41`).

### Changed

- `apps/api`: `JobHandler` now also receives the job's own id, alongside its data and transaction client, so a handler can use it as its own idempotency key for an external effect (`#40`).

### Fixed

- `apps/api`: a request's transaction committed in an `onResponse` hook, which runs *after* the response has already been sent to the client — a write's own response could be observed before its transaction had actually committed, or, on a crash in that narrow window, before it ever would. Moved to `onSend`, which runs before the response is flushed, so a response is only ever seen once its own transaction has genuinely committed (`#294`).

## [0.1.4] - 2026-09-30

### Added

- `@envelope/core`: `daysBetween` (promoted from a private helper in `computeDaysOfBuffer`) and `detectDuplicates` — matches an import's rows against an account's existing transactions, by the bank's own transaction id or otherwise the same amount within a 3-day window, each existing transaction matched at most once (`#27`).

- `@envelope/core`: `parseQif` — parses a QIF file's transactions, no column mapping needed; unlike OFX, QIF's date order and decimal separator are not standardized, so both are inferred from the file's own data first, falling back to an "ambiguous_date_format"/"ambiguous_decimal_separator" `ValidationError` asking for an explicit hint only when the file gives no evidence either way (`#30`).

- `@envelope/core`: `parseCamt053` — parses an ISO 20022 CAMT.053 statement's entries, no column mapping and no date/decimal ambiguity (ISO 20022 fixes both, unlike OFX's date order and QIF's date order and decimal separator); the counterparty name and remittance info come from the entry's first transaction detail, when the bank includes one (`#31`).
- `apps/api`: `POST .../import` accepts `format: "camt053"` (`#31`).
- `apps/api`: reconciliation — `GET /workspaces/:workspaceId/accounts/:accountId/reconciliation-candidates` lists pending and tickable cleared transactions up to a date; `POST .../reconciliations` compares the ticked total (plus the last reconciliation's own balance) against a statement balance, either completing the reconciliation on a zero difference, suggesting a pending or unticked transaction that exactly explains a real one, or resolving it with an adjustment transaction given in the same call; `POST /workspaces/:workspaceId/transactions/:transactionId/unlock-reconciliation` reopens a reconciled transaction, an audited action (`#216`) that marks its reconciliation broken until redone. A transaction's status can now only reach `reconciled` through this flow, never a direct update (`#32`).
- `apps/api`: 0.1.4's checkpoint smoke test against the real process (ADR 0007) — re-importing the exact same CSV or OFX file a second time creates no duplicate transactions, every row instead recognized as a duplicate of the one the first import already created; a negative case confirms a genuinely different, unrelated import is not mistaken for one (`#33`).

### Fixed
