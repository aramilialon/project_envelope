# 0020 — Idempotent creates: an Idempotency-Key per workspace and client batch ids

- **Status:** accepted
- **Date:** 2026-11-22

## Context

A client that retries a create after a timeout (a phone on a bad network, an assistant whose tool call is repeated, [ADR 0014](0014-assistant-access-through-mcp.md)) can record the same transaction, transfer or assignment batch twice, and the assignment ledger ([ADR 0008](0008-assignment-ledger.md)) appends a repeated batch in full. The sync protocol already answers a repeated change id with the first answer and refuses a different change under a used id, per workspace (design.md, "Field-level change protocol"; #513). The REST creates need the same rule (#559).

Client-generated entity ids would give it, but `transactions.id` is a primary key across all workspaces: refusing an id another workspace already uses would tell the caller that the row exists (as [ADR 0012](0012-trade-cash-legs.md) accepts for trades), and a transfer has two ids.

## Decision

- **An optional `Idempotency-Key` header, a UUID**, on creating a transaction (`POST .../accounts/:accountId/transactions`), a transfer (`POST .../transfers`), an assignment batch (`POST .../assignments`), quick assign (`POST .../quick-assign`), recording a scheduled transaction (`POST .../scheduled-transactions/:id/record`) and both undo routes of the ledger. A route opts in with one route option, a wrapper around its handler and one call on its success path (`apps/api/src/idempotency/route.ts`).
- **Kept per workspace.** `idempotency_keys` has the primary key `(workspace_id, key)` and the standard Row-Level Security policy: the same key in two workspaces never collides and a refusal says nothing about another workspace. Each row holds a fingerprint of the request, sha256 of the method, the route pattern, the path parameters (ids in lower case), the query, the canonical body (object keys sorted, built as key/value pairs so an own `__proto__` key is kept; non-finite numbers and nesting deeper than 32 levels refused as 400 `invalid_body`) and the user, and the reply's status and body.
- **Same key, same fingerprint:** the stored status and body are sent again with `Idempotent-Replayed: true`; nothing is written, audited or queued. **Same key, different fingerprint** (another body, route, account or member): 409 `{ "error": "id_conflict", "details": { "field": "Idempotency-Key" } }`. **A key that is not one UUID**, a repeated header included: 400 `invalid_field` with `details.field: "Idempotency-Key"`. **The header on a write route that does not take it** is refused the same way, by a global preHandler, so a client never believes a create was protected when it was not; reads ignore it.
- **Only successes are remembered.** The key is claimed in the request's own transaction and its reply stored before the reply is sent; a 4xx or 5xx rolls everything back, key included, so a corrected retry under the same key goes through. A success sent without storing its reply fails with 500 (the request transaction's onSend hook checks it), and a deferred constraint trigger refuses to commit a key with no reply, so no key can ever replay nothing.
- **Order of checks:** authentication, membership, write role, the path's own rows (404), then the key, then the body's validation and the domain checks. A replay or a conflict comes before validation on purpose: a retry of a stored success gets the same answer even when the state changed since (a category deleted, an account closed, the transaction deleted).
- **Lock order:** a request claims its key first, then its assignment batch, then takes the category-month locks (#704), then locks transactions `FOR UPDATE` in id order (#554), and the closed-account trigger's `FOR KEY SHARE` on accounts comes with its writes. A concurrent duplicate waits on the first request's uncommitted key while holding nothing else, so it cannot deadlock; it then replays the stored reply, or claims the key if the first rolled back. The wait is bounded at 5 seconds (`lock_timeout` for the claim only): beyond it, 409 `request_in_progress` with `Retry-After`.
- **Lifetime: 24 hours.** An hourly system job (`idempotency-keys-sweep`) deletes older keys, so a stored reply lives about 25 hours at most; an expired key claimed again is deleted and counts as new. As [ADR 0010](0010-system-job-workspace-enumeration.md) asks, the job sets `app.is_system_job` only to list the workspaces, then deletes each workspace's expired keys in a transaction of its own under the table's ordinary policy, which has no system-job allowance. Deleting a workspace or a user deletes their keys.
- **Assignment batch ids come from the client, as ADR 0008 decided.** `POST .../assignments` and `POST .../quick-assign` take an optional `batchId` (a UUID; otherwise the server makes one). `assignment_batches (workspace_id, id)` makes a batch id unique per workspace, and every ledger row references its batch through a composite foreign key, so every writer (a batch, quick assign, an undo) must claim one. The batch stores the fingerprint of its request (the entries, or quick assign's month, mode and scope, with the author): a repeat replays the batch's rows in the request's order (`batch_position`) with nothing appended; anything else is 409 `id_conflict` with `details: { field: "batchId", batchId }`. Batches the server made, and those from before migration 0039, have no fingerprint, so reusing their id is always a conflict.

## Consequences

- Amends ADR 0008's last consequence: a batch table now exists, as a register of ids, not as a store of totals.
- Every new create route chooses whether to take the header; until it does, the header is refused there. Trades keep `id_taken` (ADR 0012) until the assistant's draft writes (0.4.2) need a replay; then they take the same header. If 0.4.2 adds a restrictive policy for draft routes, it must still allow the claim's insert into `idempotency_keys`.
- A stored reply is a copy of workspace data (payee, memo) for about a day. It is not part of a data export and goes with the workspace or the user on deletion; in an encrypted workspace it would be ciphertext like the rest. A conflict's reply carries nothing stored, and neither the stored nor the incoming body is ever logged.
- The user mapper no longer upserts the user on every request, only when the row is missing or its email changed: the upsert locks the user's row, and would otherwise make each of a user's requests wait for the previous write that references the user (a claimed key does) to commit.
- Sync's entity creation, when it comes, keys on the change id and the device's entity id, not on this header. Ids that are unique across workspaces remain that work's problem.

## Discarded alternatives

- **Client ids on transactions and transfers:** they reveal other workspaces' ids through the global primary key, and a transfer has two.
- **An advisory lock for batches, with no constraint:** nothing in the database stops a later writer (sync) from reusing a batch id.
- **Replaying by reading the created rows again:** a later edit or delete would change the "same answer". (A batch is the exception: the ledger is append-only, so its rows read again are exact.)
- **Storing the reply in a route-level onSend hook:** its order against the hook that commits the request's transaction is a trap; the route stores the reply itself before sending it.
