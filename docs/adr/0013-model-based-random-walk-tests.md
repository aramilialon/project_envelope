# 0013 — Model-based random walk tests for the API

- **Status:** accepted
- **Date:** 2026-11-20

Extends [ADR 0007](0007-per-milestone-smoke-tests.md).

## Context

Each route of `apps/api` has integration tests, and each milestone a smoke test against the real process (ADR 0007). Both check cases someone thought of, one route at a time. The bugs that hurt most live between routes: a transfer edited on one side only, a trade whose cash leg is changed behind its back, a refusal that still wrote something, a budget month that moves when a trade is recorded on an off-budget account. `packages/core` already checks its invariants on hundreds of randomly generated histories (ADR 0003); the API had nothing that drives many routes together, in random order, and checks the whole state after each step.

## Decision

- **A seeded, model-based random walk** in `apps/api` test code, `src/test-helpers/walk/`. A generator seeded with `mulberry32` (`@envelope/core/testing`, the one every randomized test uses) picks one operation per step, in one of three workspaces whose personas are weight profiles over one shared operation set: a household that only budgets, an investor who only invests, and the main profile, a mixed household that does both and is biased towards the seam between them (transfers between the budget and the brokerage account, trades, a cash leg changed through the transactions API or sync, a reconciled leg, an edit after reconciling). A second and a third user in each workspace, an `editor` and a `read_only` member, take some of the steps. The walk is sequential: the seed alone decides the interleaving.
- **One driver interface**, `request(method, path, body, token) → { status, body }`, with two implementations: `inject` (Fastify in-process, the integration suite and CI) and `fetch` (a real HTTP connection to a running server, for a walk through the real process and for long runs). The walk never knows which one it has.
- **The model is only the log of what the API accepted**, each entity stored as the API returned it. The expected state is `@envelope/core` applied to that log: `computePositions` and the summaries, `derivedResults`, `tradeCashCents` for every cash leg, `computeBudgetMonth` for every month of the window. The model never re-implements a rule the core already has.
- **Model-free conservation checks** on the API's own answers, which need no model at all: the budget invariant (the money in the budget equals the money in the on-budget accounts), each transfer's two legs cancelling out, every cash-moving trade owning exactly one leg on its account for its cash and no leg without its trade, a brokerage account's balance being the money moved in plus its trades' cash, the account identity of the domain guide (realized + income − costs − taxes on gains = cash + cost − money moved in, with the cost of securities moved in or out), and the portfolios of an account adding up to it.
- **Refusals.** The walk predicts only the cheap rules: a `read_only` member's write and another workspace's token (403), another workspace's id (404 or 400 with its code), a sale of more than is held (the core's `validatePositionHistory` on the log plus the candidate), a reconciled leg or transaction (409), and a trade's cash leg changed or deleted through the transactions API or sync (`trade_owned_transaction`, `trade_owned`). Every other refusal must be a 4xx with a `code` from an allowlist kept next to the operation set. Every refused request, predicted or not, must leave the data as it was: a digest of every row of every table with a `workspace_id` column, per workspace, read before and after through the superuser connection (no Row-Level Security in the way), compared for every workspace the request named or could reach. `audit_log` is left out: it records attempts, not data. So is `notified_budget_problems`, written only by the `budget-recompute` job in the background, which through the real process can run while a refused request is being checked.
- **Isolation every step.** After a step that creates an entity, another persona's owner tries to reach it, with one cheap request: through their own workspace (404, and their lists and sync pull never contain it) or the victim's workspace directly (403). The full comparison then proves each workspace's lists hold exactly the model's ids.
- **Handles, not ids.** Operations refer to entities by handle (`a3`, `t12`, `tr4`), given out in the order the API accepted them; the setup of each walk is fixed code, not part of the log. A log therefore replays in fresh workspaces, where every id is new, and gives the same handles as long as the API accepts the same operations. Dates fall in a fixed past window, 2025-09-01 to 2026-04-30, since the API has no injectable clock yet; times are chosen around UTC month ends, the year end, and the two `Europe/Rome` DST changes inside the window, where a UTC date and the budget date differ.
- **Speed.** After every accepted step, the checks of the touched workspace only: the touched accounts' transactions against the model, their positions and the account identity for a brokerage account, the last month of the window against the oracle and the budget invariant for a budget write, and in the mixed household the last month of the window (which carries every earlier month over) read before and after every trade, which must leave it unchanged. A full comparison of every workspace every 100 steps and at the end. CI walks 2 fixed seeds × 300 steps through `inject` and 60 steps through `fetch` against the real process, about 55 seconds on a development machine.
- **Long and nightly runs.** `WALK_SEED` and `WALK_STEPS` run any seed for any number of steps, `WALK_DRIVER=fetch` through the real process. A scheduled, non-blocking run with a random, printed seed and more steps is a follow-up (#535); a seed that once failed joins the fixed CI seeds once its bug is fixed.
- **Reproduction.** A failure stops the walk, names the seed and the step, and writes the operation log as JSON (with the status of every step and the handles it created); `WALK_REPLAY=<file>` replays exactly those operations. A hand-written minimizer that shrinks a failing log is a follow-up (#534); no property-testing library is used (maintainer decision).
- **A bug the walk finds is excluded, never worked around.** Until it is fixed, the case it needs is left out through a named entry in `EXCLUSIONS` (`operations.ts`) that says what the bug is and where it is tracked; `WALK_INCLUDE_EXCLUDED=1` puts every excluded case back, to reproduce it or check a fix.
- **Every new route joins the operation set.** A route that writes gets an operation (generate, request, prediction, what an accepted answer adds to the model) and a weight in the profiles that would use it; a route that reads gets a check in the oracle or the conservation checks. The budget operations not yet in the walk (categories, assignments, moving money, goals, scheduled transactions), sync uploads that apply and downloads, and import are added by #533.

## Discarded alternatives

- **A property-testing library** (generators, shrinking). It would bring a dependency and its own model of state machines for something a few hundred lines of plain TypeScript do, with a log a person can read and edit by hand; the maintainer decided against it.
- **One fixed end-to-end scenario.** It checks what its author thought of, in the order they thought of it; the walk finds the orders nobody wrote down.
- **A model that re-implements the domain rules.** A second implementation of positions or of the budget month would be compared with the first and could share its mistakes; the core is already the reference, tested on its own, so the model only keeps the log.
- **Predicting every refusal.** Each rule predicted is a rule implemented twice. The cheap ones are predicted; for the rest, a refusal must carry a known code and change nothing, which is what matters to a client.
- **Random dates around today.** The API has no injectable clock, and "today" differs between runs, so a log would not replay the same; a fixed past window does.

## Consequences

- A walk takes seconds, not milliseconds: the CI step count is a trade-off between depth and the length of the test run, measured and recorded in `walk.test.ts`.
- The walk is test code that knows the API's request and response shapes; a change to a route's contract changes the walk too, as it changes the route's own tests.
- A bug found by the walk is reported with its seed and a minimal log, filed as an issue, and excluded by name until it is fixed; the exclusion list is the record of what the walk cannot cover yet.
- The walk's personas and weights are part of the test: changing a weight changes which operations a seed generates, so a recorded seed reproduces only with the operation set it was recorded with. A log, unlike a seed, keeps replaying.
