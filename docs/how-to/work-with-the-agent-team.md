# Work with the agent team

Besides the maintainer, work on `envelope` uses a small team of AI agents, each with one role. Their definitions are in [`.claude/agents/`](../../.claude/agents/). The main session acts as **coordinator**: it prepares the work, calls each role at the right moment, and takes each decision on the recommendation of the role that owns the question. **The maintainer reviews those decisions at the phase deadlines**, from the log in [`docs/team/decisions.md`](../team/decisions.md), and is still asked first about the few things listed in "Coordinator's working rules"; merges and releases follow the rules in [Work with issues, pull requests and releases](work-with-issues-and-pull-requests.md). What the team has decided and learned is kept in the repository, not in any one agent's memory ("Team memory" below).

## The roles

| Role | Agent | Writes code | When it works |
| --- | --- | --- | --- |
| Coordinator | the main session | only when it keeps an issue itself | throughout: briefs, branches, routing findings and decisions |
| Developer | `developer` | yes, on its branch | implements one issue from a written brief |
| Translator | `translator` | only the translated catalogs, new glossary terms and the copy in the mockups, on the developer's branch | after the developer, before the reviews, when the branch changes `packages/i18n/locales/en.json` |
| Architect | `architect` | no | before coding, on issues that touch schema, API, isolation, queue or sync |
| Domain expert | `domain-expert` | no | on financial rules and calculations, before and after they are built |
| UX reviewer | `ux-reviewer` | no | on a mockup before approval, and on a built screen before merge |
| Product marketer | `product-marketer` | no (proposals in its report only; may search the web) | on a new mockup before the `ux-reviewer`, on the public texts and the user-facing documents every release changed, and on one-off tasks (name and identity, a full pass over the user-facing documents, the first run) |
| QA | `qa` | no (throwaway reproduction specs only, never committed) | on every branch before its pull request is merged, and to reproduce the explorers' findings |
| Security reviewer | `security-reviewer` | no | on changes to auth, permissions, isolation, SQL, imports or dependencies |
| Integrator | `integrator` | only mechanical merge resolutions, and the release changelog | once branches have passed their reviews: orders them, brings each up to date with `main`, pushes, opens the pull request, squash-merges after green CI; on the coordinator's go, runs release steps 4 to 6 (the release changelog and its team-memory flush, with the staged notes and the lessons to prune that the coordinator hands over, and the `product-marketer`'s agreed wording for the changelog section: apply it to the compiled section; tag and GitHub release; closing the milestone) |
| Scribe | `scribe` | no (drafts in its report only) | after a triage or a `qa` report: files and edits the issues it produces; gathers the team-memory notes from the other roles' reports and drafts the entries for `docs/team/` |
| Explorer | `explorer-household`, `explorer-investor`, `explorer-mixed` | no (a browser of its own only) | before a release, once the milestone's issues are merged: uses the app as a household, an investor or a mixed household on a disposable environment and reports reproducible findings |
| Installer | `installer` | no (a shell inside its own sandbox only) | before a release whose milestone changed the install path, before every release that closes a roadmap phase, and on the install guide's pull request: installs the app by following the manuals literally on a fresh Debian 13 sandbox and reports where they fail ("Install runs" below) |

The automatic review workflow on GitHub (`.github/workflows/claude-code-review.yml`) adds one independent read of every pull request, once (see "Agents and CI").

## How an issue goes through the team

1. **Brief.** The coordinator reads the issue and writes down the acceptance criteria. Anything unclear goes to the role that owns the question (when it is not clear which role that is, the `architect` names it); only what "Coordinator's working rules" keeps for the maintainer goes to the maintainer first. The brief also lists the entries the developer adds to `docs/team/decisions.md` and the staged team-memory notes the branch carries ("Team memory" below).
2. **Design.** If the issue touches the schema, the API or isolation, the `architect` returns a plan; it also routes findings that span several roles and splits them per role. If it touches a financial rule, the `domain-expert` checks the rule with numeric examples, starting from `docs/domain-guide.md`; it judges whether the money is right, and whether the change keeps the no-advice and no-external-references rules, and a ruling it gives that is accepted lands in `docs/domain-guide.md` in the same pull request as the change. If it adds or changes a screen without an agreed mockup, a mockup is proposed in its own pull request, read first by the `product-marketer` (does it communicate what it does and why it matters) and then by the `ux-reviewer` (conformance, tokens, accessibility), and approved by the maintainer. The marketer's accepted proposals are built on that same pull request by a developer; on a screen the `ux-reviewer` decides, and a disagreement between the two is logged. A mockup approval pull request carries screenshots of each new or changed state, in both themes, on a 360 px phone and on a desktop, in a temporary folder `docs/ux/review/<pr>/` shown in its description; a last commit removes the folder before the merge ([`docs/ux/README.md`](../ux/README.md)).
3. **Build.** When the brief is clear (plan and mockup agreed), the `developer` builds it on its branch and reports. When a screen changes, the developer also updates the mockup's copy and the reference screenshots in both themes (`scripts/screenshot-demo.ts`, `scripts/screenshot-mockups.ts`) in the same pull request, and before reporting checks its own work against the `qa` edge cases and, for the web app, the `ux-reviewer`'s accessibility and screenshot items. Exploratory issues, where the brief would cost as much as the work, stay with the coordinator.
4. **Translate.** If the branch changes interface text, the developer has written it in English only and regenerated `packages/i18n/locales/en.json` ([ADR 0015](../adr/0015-english-first-translations.md)). The coordinator then runs the `translator` on the same branch and worktree, once the developer has reported: it writes Italian, German, Spanish and French, following `packages/i18n/glossary.md`, and leaves `pnpm --filter @envelope/i18n check` green. See "Translations" below.
5. **Verify.** On the finished, translated branch: `qa` always; the `ux-reviewer` if a screen changed; the `security-reviewer` whenever the change touches `apps/api/migrations/`, the authentication or permission modules, Row-Level Security policies or triggers, `pnpm-lock.yaml` or a `package.json`, or import code; the `domain-expert` again if a calculation was built. Reviewers run independently of each other and of the developer's report, so `qa` and the `ux-reviewer` run in parallel.
6. **Fix and decide.** The coordinator sends must-fix findings back to the developer. A finding that needs a decision is settled with the role that owns it, and logged in `docs/team/decisions.md`; a disagreement between roles is worked out with them, and one that stays open is logged there as a disagreement, with both positions. Only what "Coordinator's working rules" keeps for the maintainer goes to the maintainer. When the developer's context is already very large (hundreds of thousands of tokens), the coordinator does not resume it: it starts a fresh `developer` on the same branch and worktree, with a precise brief (the findings to fix, the files involved, what must not change), since a fresh agent with a short brief works more reliably than one carrying the whole history. A fix that changes interface text goes through the `translator` again before the reviews that found it look again.
7. **Integrate.** The coordinator hands the reviewed branches to the `integrator`, with each one's issue, worktree, review summary and developer. The integrator never works in a branch's worktree while that branch's developer is still running. The integrator decides the order (issue dependencies, migration numbers, files several branches change), brings each branch up to date with `main` (a rebase only before the branch is first pushed, a merge of `main` afterwards; never a force-push), resolves only mechanical conflicts such as two entries added to the same changelog or list, and sends every other conflict back to the developer with the files and what changed on `main`. It then pushes, opens the pull request saying which reviews ran and what they found, waits for CI, squash-merges, and re-checks the branches still waiting, since `main` has moved. Finding out whether branches can hurt each other is the integrator's own job, not CI's. It looks at all the ready branches together, not pair by pair: besides overlapping files, it lists what each branch changes that other code uses (exported functions and types, API shapes, schema and RLS, job payloads, i18n keys, shared styles, test fixtures) and searches all the other branches for uses of it. Every branch with no such interaction goes into one batch; the integrator merges the whole batch together in a throwaway worktree and runs the full test suite there once, then opens all their pull requests at once, so their CI runs in parallel, and merges each as soon as it is green. A waiting branch is brought up to date with `main` and re-tested only when what landed meanwhile interacts with it, never just because `main` moved. Only branches that interact are integrated one at a time. A red CI run on `main` after a merge stops the merges and counts as an interaction the integrator missed.

### Translations

For an issue that changes interface text the order is: `developer` → `translator` → `ux-reviewer` and `qa` in parallel → `integrator`.

- **When the translator runs.** Only when the branch changes the English catalog: `git diff origin/main...<branch> -- packages/i18n/locales/en.json` is not empty. Otherwise (no interface text, or a screen change that reuses existing strings only) it is skipped, and the coordinator says so in the brief to the reviewers.
- **What it gets.** The issue, the branch and its worktree. It writes every key the diff adds and re-translates every key whose English text changed, in every catalog that exists; for a screen whose mockup was approved in Italian before ADR 0015, it takes the Italian from the commit recorded in `docs/ux/README.md`. It never edits code: strings joined by hand, a word order only English allows, or a formatting problem come back in its report, and the coordinator sends them to the developer (a currency rule, to the `domain-expert`), then runs the translator again on what changed.
- **The mockups' copy.** The translator may also edit the copy in `docs/ux/mockups/*.html` (text nodes and the `aria-label`, `title` and `alt` attributes), never their structure, CSS or scripts, and reports mockup wording that no longer matches the catalogs. The developer owns the mockup's copy when a screen changes (step 3); turning all the mockups into English is its own issue (#622), going `developer` → `translator` → `ux-reviewer`.
- **Who reviews what.** Italian is read by the maintainer when reviewing the pull request; German, Spanish and French only by the agents (the translator, then the `ux-reviewer`, which looks at every language and at German on a 360 px phone). The pull request says which languages were machine-translated.
- **Branches started before ADR 0015.** Their developer was briefed to write the Italian; it keeps doing so, and the translator adds the other languages and checks the Italian against the glossary.
- **Tooling.** The [`packages/i18n` README](../../packages/i18n/README.md) describes the shipped list and review status (`locales/index.json`), extraction (`pnpm --filter @envelope/i18n extract`) and the completeness check (`pnpm --filter @envelope/i18n check`, which runs on its own, not inside `pnpm test`).
- **Adding a language** (#624–#626) follows that README's "Adding a language". The translator writes the catalog while it is not shipped yet; a `developer` on the same branch adds the loader line in `apps/web/src/i18n/catalogs.ts` and the language to `shipped` and `review` in `locales/index.json`, since the translator never edits code or the shipped list; then the `ux-reviewer` checks every screen in that language.
- **Conflicts between branches** in the catalogs are mechanical for the `integrator` (union of the keys, regenerate `en.json`, re-run the i18n check), unless both branches changed the same key.

### Product and public material

- **Mockups.** The `product-marketer` reads every new mockup before the `ux-reviewer` (step 2); it never reviews built screens.
- **User-facing documentation.** The documents written for the people who use, install or discover the app, which the marketer reads as their reader would (who it is for, what they need first, whether each term is explained and each step says how to tell it worked, what is only for development or not built yet), changing wording and order only: `README.md`, `docs/README.md`, `docs/getting-started.md` and `infra/ansible/README.md` (until the install guide of `0.4.0` replaces them as the way to install), `docs/how-to/self-host-push-notifications.md`, `docs/portfolio-api.md`, the configuration and endpoint sections of `apps/api/README.md`, `docs/domain-guide.md` (for clarity only; its money rules are the `domain-expert`'s), the "Demo data seed" section of `scripts/README.md`, and `changes/unreleased/`, `CHANGELOG.md` and the release notes; later the install, upgrade and backup guides, the comments in the `.env.example` files, the presentation page and the store listings. Everything else (the design document, the ADRs, the how-to guides on working with the team and with issues, `docs/how-to/add-a-core-test.md`, `docs/team/`, `docs/ux/`, `docs/glossary.md`, the package READMEs, `apps/web/README.md`, the rest of `scripts/README.md`, `changes/unreleased/README.md`, `CLAUDE.md` and `.claude/agents/`) is written for contributors, and is not the marketer's unless a task asks for it. A one-off task gives the marketer a full pass over the whole list.
- **Releases.** After step 3 of [Releasing a milestone](work-with-issues-and-pull-requests.md#releasing-a-milestone), the marketer reviews the wording of the release's changelog entries (`changes/unreleased/`) and of every user-facing document the milestone changed (`git diff --stat v<previous release>..main -- <the documents above>`); sentences about money go to the `domain-expert`, claims about security or privacy to the `security-reviewer`; the coordinator hands the agreed wording to the `integrator` with the go.
- **Web research.** `.claude/settings.json` allows WebSearch and WebFetch on a fixed list of public reference hosts, for every agent; hosts where anyone can publish content are never added, and fetches to this machine and its network are denied. The marketer has no shell, so a page it reads cannot drive a command.
- **Names.** Candidate names, collisions and competitor research stay in the marketer's report and the coordinator's message to the maintainer, never in the repository or on GitHub; the chosen name enters the repository only once the maintainer says so. Renaming code identifiers (`@envelope/*`, database, Keycloak realm, repository) is a separate decision with its own ADR.

### Working in parallel

Independent issues may run at the same time, each with its own developer, branch and worktree. Two developers never work on the same change: not on the same issue, not on the same branch, and not on two issues that change the same code at once. Dependent issues wait for the one they depend on.

## Coordinator's working rules

These are the maintainer's standing rules for the coordinator.

- **Minimal interruptions.** Work that needs no decision goes ahead without asking. Real decisions for the maintainer are batched into one message, not asked one at a time.
- **Experts decide, the maintainer reviews.** A question is decided on the recommendation of the role that owns it (the `domain-expert` for money, the `architect` for structure, the `ux-reviewer` for screens, the `product-marketer` for the wording of public texts, and so on), and the decision is logged in [`docs/team/decisions.md`](../team/decisions.md). The maintainer reviews the log at each phase deadline (the "… MVP" releases and `1.0.0`, [Releasing a milestone](work-with-issues-and-pull-requests.md#releasing-a-milestone), step 2).
- **Through the responsible agent.** Every decision goes through the role that owns it, never around it; when it is not clear which role that is, the `architect` names it. A decision no role owns is the coordinator's alone, logged as "coordinator alone, review it".
- **Not a mere executor.** The coordinator brings its own view, including what it knows from its exchanges with the maintainer, and works towards agreement with the role. A disagreement that stays open is logged in `decisions.md` as a disagreement, with both positions, and the work follows the owning role's recommendation until the review.
- **Still ask the maintainer first** for: anything irreversible or outward-facing beyond the releases this guide already covers; any change to permissions (`.claude/settings.json`, tokens, repository settings); any cut in scope that no role recommended; and the product's name, tagline, logo and tone of voice, and any change to the design tokens or fonts.
- **Copy inside an approved mockup.** A change to the copy only, inside a mockup state the maintainer has already approved, is decided by the `ux-reviewer` and the `domain-expert` and logged in [`docs/team/decisions.md`](../team/decisions.md); it does not go back to the maintainer for approval.
- **Check before answering.** Before answering the maintainer, look up the existing issues, milestones, decisions and lessons, and cite them: the maintainer may not remember past work.
- **Report after an absence.** When the maintainer comes back, report from `decisions.md`, the pull requests merged and the issues opened since the last report's date, and the open disagreements. Every pull request description names the reviews that ran and any disagreement.
- **A fresh agent for rework**, when the original's context is very large (step 6 above).
- **Stop finished agents** ("Keeping the team tidy" below).
- **Quiet commands.** Filter command output to what is needed, and leave noisy work (full test runs, long logs) to the agents, whose reports carry only the conclusion.

## Team memory

What the team has decided and learned lives in [`docs/team/`](../team/), so that every agent, and every new session of the coordinator, starts from it. The coordinator reads both files before coordinating; every agent reads the lessons tagged `[all]` and those tagged with its own role before it starts.

- **[`decisions.md`](../team/decisions.md):** the decisions taken without the maintainer, one line each with its issue, date and the role that recommended it, grouped by the phase deadline that reviews them and then by milestone; open disagreements at the top of their section. At the phase review the coordinator empties the section through a pull request whose description gives each entry's outcome: confirmed; confirmed and moved into an ADR or the design text (named); or reversed, with the new issue that reverses it.
- **[`lessons.md`](../team/lessons.md):** traps an agent hit and what to do about them, tagged with the role they concern or `[all]`, each naming the file it should be promoted to. The pull request that fixes a lesson's cause, or promotes it into its file for good, deletes it; at each release the coordinator lists the lessons nobody hit in the last two milestones, and the integrator deletes them. At most 40 entries, about 150 lines.
- **Who writes.** The `developer` and the `translator` write on their own branch: the decision entries their brief lists, the lessons they hit, and the deletion of the lessons their change fixes. The read-only roles and the `integrator` end their report, when they have something, with **Notes for the team memory**: at most three items, each with its wording and its target file. The explorers do the same through their shared instructions. The `scribe` gathers and dedups these notes and drafts the entries in its report.
- **Flush.** The coordinator saves each note in its private staging notes as soon as the report arrives, and adds the staged notes to the next branch it briefs, preferably the next one in the same area; never to a branch already reviewed or to a batch the integrator has already tested. The release changelog pull request ([Releasing a milestone](work-with-issues-and-pull-requests.md#releasing-a-milestone), step 4) is the backstop: with the go, the coordinator hands the `integrator` whatever is still staged and the list of lessons to prune, and the release changelog pull request applies both (the release changelog and its team-memory flush). Once a note is on `main`, the coordinator removes it from its private notes.

## Agents and CI

Role agents run locally, on the developer machine and on disposable environments, never as new CI jobs: the maintainer's rule is to keep the overall cost, in money and tokens, as low as possible.

- The automatic AI review on GitHub (`.github/workflows/claude-code-review.yml`) gives every pull request one independent read, once, when it is opened or marked ready, not again on every push. It may read the pull request (`gh pr diff`, `gh pr view`) and the checked-out files, and post inline and summary comments; it runs no other commands and cannot change the repository.
- Every review ends with a comment on the pull request: its findings, "No issues found", or one line "Not reviewed: <reason>". The review may skip a pull request it judges not to need one (a trivial change, a closed or draft pull request, one it already commented on), but its prompt makes it say so, since the review command would otherwise stop silently (#618; the maintainer chose this over reviewing every pull request, to keep the cost down). A "Not reviewed" comment counts as the review having run: no re-trigger. The full output stays hidden, because the repository is public.
- The `integrator` (or the coordinator) checks for the comment with `gh api repos/<owner>/<repo>/issues/<n>/comments --jq '.[].user.login'`, one query per command, and looks for `claude[bot]`; inline comments are under `pulls/<n>/comments`. When there is none: a pull request opened with a merge conflict starts no review at all, since GitHub runs no `pull_request` workflow until the conflict is resolved, so bring the branch up to date, then re-trigger with `gh pr ready --undo` and `gh pr ready`; a run that ended green without any comment is re-triggered once the same way. Either re-trigger happens at most once per pull request; if the review is still silent, merge on green CI and the local reviews, and say in the report that the AI review did not comment, with the run id.
- Dependencies are audited weekly by a token-free workflow (`.github/workflows/security-audit.yml`, `pnpm audit`) that keeps one issue open with its findings; the team fixes them locally like any other issue.
- Exploratory runs, QA and the security review stay local.
- Before every release the coordinator also checks the open Dependabot, code-scanning and secret-scanning alerts ([Releasing a milestone](work-with-issues-and-pull-requests.md#releasing-a-milestone)): the `security-reviewer` triages them, each real one is fixed by a `developer` through the usual reviews, and the maintainer approves any dismissal.

## Exploratory runs before a release

Once a milestone's issues are merged, and before its release, the coordinator runs the explorers (this run replaces the maintainer's own testing, except before the releases that close a roadmap phase; see [Releasing a milestone](work-with-issues-and-pull-requests.md#releasing-a-milestone)) on a disposable environment ([scripts/README.md](../../scripts/README.md), "Disposable environments"): all three agents every release, one per persona, `explorer-household`, `explorer-investor` and `explorer-mixed`, each with a step budget of about 100 steps and the reference material the explorer's expectations must come from (the design document's user-interface section and mockups, and the API documentation for features with no screen yet).

- **Distinct charters.** Each persona has a standing charter of its own, written into its definition: the household covers the permission matrix (owner, editor, reader) and the credit card flows; the investor covers trades, positions, closing accounts and the net-worth rules; the mixed household covers transfers, closed accounts and every place where the budget meets the portfolio. On top of that, the coordinator gives all three what the release itself changed, the flows to cover and the odd cases to try.
- **Duplicates.** Before `qa` reproduces anything, the coordinator merges the findings that two or three explorers reported for the same problem, keeping every explorer's steps.

- Each explorer has a browser of its own and nothing else: no shell, no source code, no credentials beyond the environment's own personas. Its browser is its own Playwright MCP server (`playwright-household`, `playwright-investor`, `playwright-mixed` in [`.mcp.json`](../../.mcp.json)), and its definition lists only that server's tools, so it cannot reach another explorer's browser. The three run at the same time without sharing tabs, so the coordinator starts them in parallel; each closes its browser with `browser_close` when it is done, which ends only its own. Every server is the pinned devDependency of `@envelope/scripts` started by [`scripts/explore-env/playwright-mcp.sh`](../../scripts/explore-env/playwright-mcp.sh) with the same confinement: headless, an in-memory profile, `file://` blocked, ordinary requests kept on loopback, no listening port, and every file its tools write (snapshots, screenshots, script results) confined to a throwaway temporary directory of its own, never the repository. Install its browser once with `pnpm --filter @envelope/scripts exec playwright-mcp install-browser chrome-for-testing`. The server tools nobody needs (running arbitrary code, uploading or dropping files, reading full request headers) are denied for every server in `.claude/settings.json`.
- The three definitions share one set of instructions, kept in [`scripts/explore-env/explorer-instructions.md`](../../scripts/explore-env/explorer-instructions.md): an explorer has no tool to read a file, so `pnpm --filter @envelope/scripts explore:agents` writes the text into each `.claude/agents/explorer-<persona>.md`. Edit the instructions (or `explorer-agents.ts` for the header and the tools), never the generated files; `pnpm test` fails when they drift apart, or when `.mcp.json` or the deny list does not match.
- Claude Code asks the maintainer to approve a project MCP server from `.mcp.json` before using it: after a change to the servers (such as the one that introduced the three browsers), approve the new ones when Claude Code asks, or with `/mcp`. `claude mcp reset-project-choices` asks again for all of them.
- Keep the web app's Vite dev server stopped during a run: it serves repository files to any local page.
- The coordinator brings the environment up and down with `explore:up` and `explore:down`, and never hands the explorer the manifest file itself, only the URLs, the persona credentials and the workspace ids from it.
- Every finding must name the source of its expectation. `qa` reproduces each one on a disposable environment of its own (`explore:up`, then `explore:down` when done): through the API with `curl`, or, for what only a screen shows, with a throwaway Playwright spec in its own scratch worktree, never committed, run against that environment with `E2E_MANIFEST`. It reports each finding as reproduced or not, with the exact steps ([`.claude/agents/qa.md`](../../.claude/agents/qa.md), "Reproducing an explorer finding"). Only reproduced findings become issues (the `scribe` files them from `qa`'s report), and spec gaps and product questions go to the maintainer. Each reproduced bug is then fixed by a `developer`, from a brief like any other issue, and goes through the usual reviews; the coordinator does not fix findings itself. Every bug that gets fixed gets a deterministic test (an integration test, an e2e spec or a random-walk seed): explorer runs never gate a merge.

## Install runs

The `installer` agent is a self-hoster who installs `envelope` by following the install manuals literally, on a fresh Debian 13 machine, and reports where they fail as written, are stale, unclear, assume knowledge, or make the reader leave them. Until the install guide of `0.4.0` exists, it tests the development guide: `README.md`, then `docs/getting-started.md`, cloning the public repository over HTTPS.

- **When.** Before a release whose milestone changed the install path (the getting-started guide, the Ansible playbook, `infra/`, the `.env.example` files, the Node.js, pnpm or Docker requirements), before every release that closes a roadmap phase, and on the pull request of the `0.4.0` install guide. Only when the machine has capacity to spare: never at the same time as the explorers or a full test suite, since the sandbox takes 2 CPUs, 4 GB of memory and at least 12 GB of disk.
- **Its machine.** The sandbox is a privileged Debian 13 container with systemd and a Docker Engine of its own, on its own bridge, kept off the private networks by a host firewall; the internet stays reachable ([scripts/README.md](../../scripts/README.md), "Installer sandbox"). The agent's only tool is `mcp__installer-sandbox__run` (the `installer-sandbox` server in [`.mcp.json`](../../.mcp.json), allowed in `.claude/settings.json`), which runs one command inside that container as `root` or `dev`, and nowhere else. The confinement is that tools list, not a Bash allow rule: allow rules apply to every agent of the session.
- **The coordinator** brings the sandbox up with `pnpm --filter @envelope/scripts install:up` (once per host, as root, `node scripts/install-env/cli.ts firewall-on` first) and down with `install:down` when the run and `qa`'s reproductions are over. Its brief gives the installer the repository's public URL, the manual to start from, the two passwords `install:up` printed, a step budget of about 150 tool calls, and the known differences between the sandbox and the manual's machine, which are not findings: there is no hypervisor, so `qemu-guest-agent` and "use a VM rather than an LXC container" do not apply; there is no laptop, browser or second device, so SSH keys from a laptop, SSH tunnels, LAN access, mkcert and Caddy are not covered; and whether the manual's SSH clone counts as a finding.
- **Findings.** Each has a category (fails as written, stale, unclear, assumes knowledge, had to leave the manual), a severity (blocker, major, minor) and the exact commands. The transcript of every command is in `$TMPDIR/envelope-installer/` (or `ENVELOPE_INSTALLER_TRANSCRIPT`), never in the repository. "Fails as written" and "stale" findings go to `qa`, which reproduces them in a fresh sandbox from the transcript; the other categories are judgment calls, which go to the `product-marketer` for the wording and then to the `scribe`, who files the issues. A fix to a command, a setting or a technical claim goes through a `developer` and the usual reviews like any other change.

## Keeping the team tidy

- Every agent with a shell stops its own background work before returning (the "Before you return" section of each definition): no test run, server, CI watch or disposable environment of its outlives it.
- Once a branch is merged, the coordinator stops that branch's agents (`TaskStop`) and removes its Git worktree under `.claude/worktrees/` (`git worktree remove <path>`, which keeps the branch and its history), so the list of agents and that folder show only work in progress. The folder is ignored by Git and never committed.
- The coordinator regularly compares the running agents with the reports it has received. An agent that ended without a report, or that has been waiting much longer than its task needs, is chased at once: a hang is a finding in its own right.

Small changes (a typo, a dependency bump with no code change) skip the team: the coordinator handles them directly. The release changelog is the `integrator`'s ([Releasing a milestone](work-with-issues-and-pull-requests.md#releasing-a-milestone), steps 4 to 6).

## Changing the team

The definitions are ordinary Markdown files with a short header (name, description, allowed tools, and a `model` only when a role needs one other than the default). Change them through a pull request like any other file. A role that keeps finding nothing useful is a candidate for removal; a kind of mistake that keeps reaching `main` is a candidate for a new check in the role that should have caught it. A trap is first written down in [`docs/team/lessons.md`](../team/lessons.md); one that keeps being hit is promoted into the definition or guide its entry names, and the pull request that promotes it deletes the entry.
