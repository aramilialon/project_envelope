# @envelope/api

The backend server: a Fastify HTTP API on top of PostgreSQL. Steps 1 to 4 of the backend MVP (see `CLAUDE.md`) are done: configuration, a database pool, a migration runner, the domain schema and Row-Level Security per workspace, and authentication — Keycloak access tokens verified against the realm's JWKS, mapped to a local `users` row, workspace membership checked with the request's Row-Level Security session variables set. Token verification and user mapping are global preHandlers, applied to every route except `/health`; workspace membership stays an explicit per-route opt-in. Step 4, the Budget API: accounts, with their payment category and optional starting balance for on-budget credit cards; category groups and categories, sortable and archivable; transactions, with splits, income, reconciliation locking and transfers between accounts; the assignment ledger, an append-only record of assign/unassign/move money, with undo; the budget month itself, computed by `@envelope/core` from all of the above, plus its own list of unresolved problems, derived from that same computation; goals (targets), one per category, joined with how much each still needs this month; days of buffer, recomputed from real transactions; quick assign, funding a whole scope of categories in one ledger batch; scheduled transactions (rent, salary, subscriptions), reserving money in their category ahead of being recorded, now firing automatically on their own due date (#38). Every endpoint that changes budget data rejects a `read_only` member; `owner` and `editor` can write, everyone can read. Step 5 (Import) has started: CSV files, given a column mapping remembered per account, and OFX, QIF and CAMT.053 statement downloads, self-describing and needing no mapping, are staged with duplicate detection against the account's existing transactions before being confirmed into real transactions. Reconciliation ties a statement's closing balance to the cleared transactions up to that date, resolving a real leftover difference with an adjustment transaction; unlocking a reconciled transaction is a separate, audited action. Step 6 (Queue and notifications) has started: a `QueueDriver` interface (`enqueue`, `schedule`, `work`) behind which the rest of the code never sees pg-boss directly, now wired into `main.ts` and creating a transaction or a transfer, which queues a `budget-recompute` job in the same database transaction as the write that triggers it. Every job delivery is idempotent by construction: `processed_jobs` discards a repeat before its handler ever runs. Push notification delivery has one interface and, for now, one real adapter — Web Push, keyed by the triggering job's id so a duplicate delivery coalesces on the device instead of showing twice; APNs and Android/FCM are stubs until the mobile app (0.3.0) gives them a real device to send to. The `budget-recompute` job now runs for real: it notifies every workspace member when a category goes negative, a purchase exceeds the available balance, or money arrives to assign, but only when that problem is new or its amount has changed since the last time. Step 7 (Sync) is done for its own milestone's scope (`transactions.memo`/`transactions.payee`; every other field and entity is added only once something needs to sync it): `change_log`, one row per field-level change (entity id, field name, hybrid logical clock, device id, value), idempotent on the change's own id so a repeated network retry never duplicates a record; `POST /workspaces/:workspaceId/changes` applies a device's own queued changes by clock alone, converging to the same result whatever order they arrive in, rejecting one against a reconciled transaction outright; `GET /workspaces/:workspaceId/changes` is the download side, every change later than the clock a device last saw. Certified end to end by a real two-device smoke test: offline edits, including a genuine conflict, converge to the same result on both sides with nothing lost or duplicated.

The portfolio endpoints (instruments, portfolios, trades, positions, brokerage accounts' tax regimes) are documented for their users, with bodies, examples and validation codes, in [docs/portfolio-api.md](../../docs/portfolio-api.md).

## Commands

```bash
pnpm --filter @envelope/api dev          # start with auto-restart on file changes
pnpm --filter @envelope/api start        # start once
pnpm --filter @envelope/api migrate      # apply pending migrations
pnpm --filter @envelope/api fx-rates:import <file.xml>   # load a downloaded ECB rates file (see "Administration")
pnpm --filter @envelope/api test         # integration tests, then smoke tests, each in its own clearly separated node --test run
pnpm --filter @envelope/api test:integration   # only the integration tests, several files at once (API_TEST_CONCURRENCY, ADR 0016)
pnpm --filter @envelope/api test:smoke         # only the smoke tests (ADR 0007) — CI runs these as their own named step
pnpm --filter @envelope/api typecheck
```

### Giving `envelope_app` (and `envelope_queue`) a login

Migrations create the `envelope_app` and `envelope_queue` roles but deliberately never give them `LOGIN` or a password (ADR 0006: that would mean committing a real credential to the repository). Do it once per Postgres instance, the same way `infra/.env` already holds the `envelope` and Keycloak passwords:

```bash
$ docker exec -it envelope-postgres-1 psql -U envelope -d envelope \
  -c "ALTER ROLE envelope_app WITH LOGIN PASSWORD '<a password you pick>';" \
  -c "ALTER ROLE envelope_queue WITH LOGIN PASSWORD '<a different password you pick>';"
```

Roles are shared by the whole Postgres instance (not per database), so this one command covers both the `envelope` and `envelope_test` databases. Use those passwords in `APP_DATABASE_URL` and `QUEUE_DATABASE_URL`.

## Running the integration tests locally

The tests need their own database, separate from the one used for everyday development, so a broken test never touches real data. They also need `KEYCLOAK_ADMIN_PASSWORD` (the value from `infra/.env`): the tests provision and tear down their own realm through the admin API, so no manual realm setup is needed to run them.

```bash
$ createdb -h 127.0.0.1 -U envelope envelope_test   # once, asks for the password in infra/.env
$ DATABASE_URL=postgres://envelope:<password>@127.0.0.1:5432/envelope_test \
  KEYCLOAK_ADMIN_PASSWORD=<password from infra/.env> \
  pnpm --filter @envelope/api test
```

CI does the same against a fresh PostgreSQL service container and a Keycloak container it starts first and waits on only after installing and migrating, so its boot overlaps with them: see `.github/workflows/ci.yml`.

The integration test files run concurrently ([ADR 0016](../../docs/adr/0016-integration-test-files-run-concurrently.md)): as many at once as `API_TEST_CONCURRENCY` says, and when it is not set, Node.js's own default, the available cores minus one (at least one). On a 6-core development machine the run took 436 s one file at a time and 153 s at the default of 5 (#638). `API_TEST_CONCURRENCY=1` runs them one at a time again, to check whether a failure comes from two files sharing something. The smoke tests still run one file at a time.

Every integration test file must therefore be safe to run alongside every other one:

- It creates the data it needs (workspaces, users, instruments with random tickers, Keycloak users) and removes only that data; it never counts, lists or deletes rows across the whole database, and never assumes a table holds only its own rows.
- Code under test that reads the whole database — a job that enumerates every workspace, a migration applied to existing rows, the migration runner itself — runs on a throwaway database of its own (`createIsolatedDatabase`, `src/test-helpers/isolated-database.ts`), as `fire-job.test.ts`, `double-delivery.test.ts`, `migrate.test.ts` and the `migration-*.test.ts` files do.
- A file that starts the real API process (`src/main.ts`) runs it on a throwaway database too, as the random walk's `fetch.test.ts` does (`useWalkSuite({ isolatedDatabase: true })`): the process starts the queue workers (`budget-recompute`, ...) and the hourly `scheduled-transactions-fire` schedule, which in the shared database would take jobs other files queued.
- A queue worker it starts may receive jobs another file queued, and must not depend on being the only worker of its queue, nor wait for a queue to be empty.
- It never waits a fixed time for a job to arrive or not to arrive. Whether a job was queued, deduplicated or rolled back is read from pg-boss's own rows (`pgboss.job WHERE name = <the test's own job type>`), and whether it was processed from `processed_jobs`, polled with a bounded timeout and a failure message that says what it waited for (#641). A test that needs a real delivery gives the driver a short `pollingIntervalSeconds` (0.5, pg-boss's minimum), as `postgres-driver.test.ts` does.
- It never changes anything that belongs to the whole server (a role's login or password, a server setting): see the login roles below.
- It never changes anything realm-wide in Keycloak (the realm's settings, its clients, its keys): every file of a run shares one realm (below). It changes only the Keycloak users it created through `setUpKeycloakTestRealm()`; a test that needed a realm setting of its own would have to create a realm of its own with `createTestRealm` and delete it.
- It calls `runMigrations` before it uses the database, like every other file: the runner holds an advisory lock, so the files of a run wait for each other and apply each migration once.

A new file that breaks one of these rules makes some runs fail and not others. A long file holds up the end of the run: split it, as the random walk is split into one file per seed or check (below), rather than letting it grow past the slowest of the others (about 35 s today).

Several runs can share one machine at the same time, each against a database of its own (for example `envelope_test_a` and `envelope_test_b`): the smoke tests listen on ports the operating system picks, each test database gets login roles of its own (below), and the two job test files that fire every workspace (`fire-job.test.ts`, `double-delivery.test.ts`) create and drop a throwaway database of their own, named after `DATABASE_URL`'s with a random suffix. The `DATABASE_URL` user therefore needs to be allowed to create databases, as the `envelope` superuser and CI's own are. Each run uses as many processes as the machine has cores, so set `API_TEST_CONCURRENCY` lower for each when running two at once.

The tests never log in as `envelope_app` or `envelope_queue`, and never change their login or password: roles belong to the whole PostgreSQL server, so a run that set them changed them for every other run on that server and for a dev server too. A real server another run had started then failed to open new connections (`28P01`, "password authentication failed") and answered 500 (#585). Instead, each test database gets two login roles of its own, `envelope_app_t<16 hex digits>` and `envelope_queue_t<16 hex digits>`, members of `envelope_app` and `envelope_queue`, so every grant and Row-Level Security policy for those applies to them. Their names come from `DATABASE_URL`'s server and database, their passwords from the name and `DATABASE_URL`'s own password, so every test file of a run computes the same pair, and `APP_DATABASE_URL`/`QUEUE_DATABASE_URL` play no part in the tests. Each role's comment names its database; when a run creates a pair, it drops the pairs whose database no longer exists. `DATABASE_URL` must therefore include the superuser's password (a password from `PGPASSWORD` or `~/.pgpass` alone is refused): without it the derived password would be a constant anyone with the repository could compute. Like `envelope_app` itself, a test role can connect to every database on the server that lets `PUBLIC` connect, the shared `envelope` one included, with `envelope_app`'s or `envelope_queue`'s privileges; its password can be derived only by someone who already has the superuser's. In a test database, pg-boss's `pgboss` schema and tables are owned by the run's test queue role when that run created them (a role that still owns something in a database that exists is never dropped). To list them:

```bash
$ psql "$DATABASE_URL" -Atc "SELECT rolname, shobj_description(oid, 'pg_authid') FROM pg_roles WHERE rolname ~ '^envelope_(app|queue)_t[0-9a-f]{16}$'"
```

The rule for anything that runs tests or scripts against a shared PostgreSQL server: never `ALTER ROLE` a role another run or a dev server may be logged in as. Give the run a role of its own instead, as the tests and the disposable environments (`scripts/explore-env/`) do.

A run killed before its job tests finish can leave a throwaway database behind, named `<DATABASE_URL's database>_` followed by 12 hex digits. To list and remove them (here for `envelope_test`):

```bash
$ psql "$DATABASE_URL" -Atc "SELECT datname FROM pg_database WHERE datname ~ '^envelope_test_[0-9a-f]{12}$'"
$ psql "$DATABASE_URL" -Atc "SELECT format('DROP DATABASE %I WITH (FORCE);', datname) FROM pg_database WHERE datname ~ '^envelope_test_[0-9a-f]{12}$'" | psql "$DATABASE_URL"
```

### One Keycloak realm per run

`test:integration` and `test:smoke` each create one throwaway Keycloak realm for the whole run, not one per test file (#639): the runner's global setup (`--test-global-setup=src/test-helpers/keycloak-global-setup.ts`) creates it with its three clients before the first file starts, and hands its name and client secret to every file through `ENVELOPE_TEST_KEYCLOAK_REALM`. Each file then gets a user of its own in it from `setUpKeycloakTestRealm()`, and more users from `createUser()`/`getTokenForNewUser()`, so the files of a run never share a user. Creating and deleting a realm with its clients cost every file about 1.3 s in CI and 3.4 s locally, and many files doing it at once made Keycloak answer 500 now and then (#519). With `API_TEST_CONCURRENCY=3` on a 6-core development machine, the integration run went from 182 s to 117 s and the smoke run from 41 s to 25 s.

A file run on its own (`node --test <file>`, without the global setup) creates a realm of its own instead and deletes it when it ends, as every file did before.

The global teardown deletes the run's realm once the last file has ended, also when a file fails or the run is interrupted with Ctrl+C (SIGINT) or SIGTERM. A run killed outright (SIGKILL, a crash of the runner itself) leaves its realm behind, so every global setup first sweeps the leftovers: a test realm is named `envelope-test-run-<host>-<pid>-<start>-<random>` (a hash of the host name and PID namespace, the creating process, its start time). The sweep keeps a realm whose process on this host is still running, however long it has run, and deletes one whose process is gone, or whose process id now belongs to a process started after the realm (read from `/proc`). A realm from another host, whose process it cannot check, is deleted once it is older than 24 hours, the same limit as `explore:sweep`. Realms named `envelope-test-<uuid>`, one per file from before #639, are deleted once one of their users is older than 24 hours. To list the test realms by hand:

```bash
$ TOKEN=$(curl -s -d grant_type=password -d client_id=admin-cli -d username=admin \
    --data-urlencode "password=$KEYCLOAK_ADMIN_PASSWORD" \
    http://127.0.0.1:8080/realms/master/protocol/openid-connect/token | jq -r .access_token)
$ curl -s -H "Authorization: Bearer $TOKEN" 'http://127.0.0.1:8080/admin/realms?briefRepresentation=true' | jq -r '.[].realm | select(startswith("envelope-test-"))'
```

## The random walk

`src/test-helpers/walk/` drives the API with a seeded random walk ([ADR 0013](../../docs/adr/0013-model-based-random-walk-tests.md)): three workspaces (a household that only budgets, an investor who only invests, a mixed household that does both), each with an owner, an editor and a read-only member, take a few hundred steps between them, one operation per step, in an order the seed decides. After every step it checks the touched workspace against `@envelope/core` applied to what the API accepted, plus the checks that need no model (the budget invariant, a transfer's legs, a trade's cash leg, a brokerage account adding up), that a refused request changed nothing and that another workspace cannot see what the step created; every 100 steps and at the end it compares everything.

It runs with the integration tests, with the same environment (`DATABASE_URL`, `KEYCLOAK_ADMIN_PASSWORD`), as one test file per seed or check, so the walks run alongside each other and the other files ([ADR 0016](../../docs/adr/0016-integration-test-files-run-concurrently.md)): `seed-1.test.ts` and `seed-20261120.test.ts`, 300 steps each through `inject`; `determinism.test.ts`, one seed walked twice for 60 steps (the two operation logs must be byte-identical: a seed is a reproduction only if it gives the same walk every time); `regressions.test.ts`, every regression log in `src/test-helpers/walk/regressions/` replayed; and `fetch.test.ts`, 60 steps through `fetch` against the real server process, on a throwaway database of its own. Each file builds its own app and Keycloak users, in the run's one realm, through `suite.ts`; a seed takes about 22–33 s, the other files less. A new CI seed, or a new kind of check, gets a file of its own in the same shape (`useWalkSuite()` at the top of its `describe`), never a second test in an existing file. `walk.test.ts` walks only on demand, and is skipped in a normal run. To run the walks on their own, or longer:

```bash
$ cd apps/api
$ node --test --test-global-setup=src/test-helpers/keycloak-global-setup.ts 'src/test-helpers/walk/*.test.ts'  # what CI runs (with model.test.ts), in one realm
$ WALK_SEED=4242 WALK_STEPS=3000 node --test src/test-helpers/walk/walk.test.ts    # any seed, any length
$ WALK_SEED=4242 WALK_DRIVER=fetch node --test src/test-helpers/walk/walk.test.ts  # through the real process
```

Each walk prints its steps, how many were accepted and refused per operation, and how long it took. A failure stops the walk and prints the seed, the step, the operation, what did not hold, and the path of the operation log it wrote (in the system's temporary directory, or `WALK_LOG_DIR`). The log is JSON: every operation with its parameters, entities named by handle (`a2` is the workspace's second account, `t5` its fifth transaction, `tr3` its third trade, `p1` its first portfolio, `c4` its fourth category, `i1` to `i3` the shared instruments), the status the API answered and the handles each step created. Replay it, in fresh workspaces:

```bash
$ WALK_REPLAY=/tmp/envelope-walk-seed4242-step812-….json node --test src/test-helpers/walk/walk.test.ts
```

To report a bug, cut the log down by hand to the few steps that still fail (keep `version`, `seed` and `driver`; the setup of each workspace is not in the log, so a log can start from its first step), replay it to check, and attach it to the issue. `WALK_KEEP=1` leaves the workspaces in the database after the walk, to look at them with SQL.

A bug the walk finds and that is not fixed yet is left out by a named entry in `EXCLUSIONS` (`src/test-helpers/walk/operations.ts`), saying what the bug is and where it is tracked. Remove the entry with the fix; `WALK_INCLUDE_EXCLUDED=1` puts every excluded case back, to reproduce one or check a fix. None is excluded today: the walk's first two findings, `transfer-leg-amount` (#547, editing the splits of one leg of a transfer left the other leg as it was) and `card-income` (#548, income on an on-budget credit card was accepted and then every budget month of the workspace answered 400), are fixed, and the walk now predicts the fixed behaviour (#580): a new amount on a transfer leg gives the other leg the opposite amount and sends a cleared other leg back to pending, or answers 409 when the other leg is reconciled; income on an on-budget card answers 400 `card_income_not_supported`. Each bug's minimal log is kept in `src/test-helpers/walk/regressions/`, named after its issue: replay it with `WALK_REPLAY` to see the bug while it is open. Once the bug is fixed, `regressions.test.ts` replays every log in that directory through `inject` on every run (a few steps each, about a second), so CI keeps them green; a log goes in that directory only with its fix, or the run fails.

### Adding a route to the walk

Every new route joins the walk (ADR 0013):

1. **A route that writes** gets an operation in `src/test-helpers/walk/operations.ts`, an `OperationSpec` with four functions: `generate` (parameters picked with `random` from the model, entities by handle; `undefined` when the operation cannot happen yet), `request` (the HTTP request, handles resolved to ids), `predict` (`ACCEPT`, a `refuse` with the status and code for a cheap rule the walk can know, or `ANY` when only the API can tell) and `accept` (first an echo check, with `expectEcho` or the `echoTransaction`/`echoTradeRow`/`echoEdit` helpers, that every field the request sent came back unchanged, then what the answer adds to the model, with `model.add…`, and which accounts, portfolios and budget it touched). Anything `generate` picks from, and any handles given out for the rows of one answer, must be in handle order, never in id or API order (`sortableHandle`), or a seed stops giving the same walk. Add it to `OPERATIONS` and give it a weight in the `PROFILES` of the personas that would use it. If an unpredicted refusal is legitimate with valid data, add its code to `REFUSAL_ALLOWLIST`, with a reason.
2. **A new entity** gets a map and handle prefix in `WorkspaceModel` (`model.ts`), and a probe in `probeIsolation` (`invariants.ts`).
3. **A route that reads** gets a check: against the oracle (`@envelope/core` on the model's log) where the core computes it, or a conservation check on the API's own answers, called from `fullCheck` and, if it is cheap, from the touched-workspace checks in `run.ts`.
4. Run a few seeds for a few thousand steps (`WALK_SEED`, `WALK_STEPS`) before opening the pull request, and keep each CI walk file under about half a minute (`CI_STEPS` and the other lengths in `suite.ts`).

## Administration

### Exchange rates

The euro reference rates (#85, ADR 0019) are public data the ECB publishes every working day around 16:00 Central European Time. With `MARKET_DATA_FETCH_ENABLED` on (the default), the server keeps them up to date by itself: the `fx-rates-fetch` job runs once at startup (skipped when the newest stored day is today or yesterday, UTC, so frequent restarts fetch nothing) and at 15:30 and 21:30 UTC on working days, loads the full history since 1999 (about 8 MB, about 200 000 rates) the first time, or after a gap of more than 80 days, and the last 90 days (about 100 kB) otherwise. A rate the ECB revised is updated, and the job logs a warning naming it; a rate already stored is left as it is. A currency the ECB stopped publishing keeps its stored rates; one replaced by another (the Cypriot pound, the old Turkish lira…) is not stored, since no account or instrument can be in it.

**What leaves the server:** one HTTPS GET for a public file, `eurofxref-hist.xml` or `eurofxref-hist-90d.xml` under `MARKET_DATA_ECB_URL`, with no cookie, token, query or anything about the server, its users or their data. The ECB sees the server's public address (for a server at home, your household's address), the time of the request and the HTTP client's generic name (`node`), as any web server would. The request follows no redirect, gives up after 60 seconds, and refuses an answer that is not XML or is larger than 32 MiB; a refused or failed fetch stores nothing, writes one error line to the server log (`exchange rates not stored`, with a refused file's `code` and `details`: `reason`, `currency`, `date`, `offset`), and the queue retries it. Every screen and endpoint reads only the stored rates: no request ever reaches the ECB.

To make no outbound request at all, set `MARKET_DATA_FETCH_ENABLED=false` and load the rates from a file downloaded elsewhere (the daily, 90-day or full history XML file from the ECB's euro reference rates page), as often as you want them updated:

```bash
pnpm --filter @envelope/api fx-rates:import ~/Downloads/eurofxref-hist.xml
# Exchange rates from /home/me/Downloads/eurofxref-hist.xml: 198706 added, 0 changed, 0 already stored.
```

It connects with `APP_DATABASE_URL` from `apps/api/.env`, like the server, and writes through the same code as the job: a file with any malformed entry is refused as a whole and nothing is stored. Loading the same file again changes nothing.

### Correcting the instruments catalog

The API never updates or deletes an instrument (#76): other workspaces may already reference it, and `envelope_app` has only `SELECT` and `INSERT` on `instruments`. An administrator corrects or removes a bad catalog row with SQL, connected as the table owner (the `envelope` role that runs the migrations, `DATABASE_URL`), never as `envelope_app`. The table has Row-Level Security forced since migration 0035 (#505): that role is a superuser (ADR 0006), so it still sees every row, workspaces' private instruments included; a private instrument (`workspace_id` set) is that workspace's data, not part of the catalog:

```bash
$ psql "$DATABASE_URL"
envelope=# SELECT id, isin, ticker, exchange, name, type, currency, price_factor_e6 FROM instruments WHERE isin = 'XS0000000000';
envelope=# UPDATE instruments SET name = 'Corrected name' WHERE id = '<id>';
envelope=# DELETE FROM instruments WHERE id = '<id>';
```

Check before a correction that it keeps every workspace's figures right: changing `type`, `currency` or `price_factor_e6` changes how every holding of that instrument is valued and taxed, in every workspace; a change to `price_factor_e6` also revalues every stored price of it (`prices.close_e6` is quoted with the instrument's price factor applied on top, #82), shared and workspace prices alike. A row that trades or prices still reference cannot be deleted (#77, #82: neither foreign key has an `ON DELETE` action); correct it in place instead. Never change a row's `workspace_id`: the triggers of migrations 0034 and 0035 check a trade or a price when it is written, not its instrument afterwards, so making a shared instrument private would hide it from every other workspace that already trades it, and making a private one shared would show it to all.

### Income on a credit card stored before #548

`@envelope/core` does not model income on a credit card yet (`packages/core/README.md`, "Known limitations"), so the API refuses it on every write path with 400 `{ "error": "card_income_not_supported", "details": { "accountId": "<card>" } }`: a transaction, or a scheduled transaction, with a single split and no category (`categoryId: null`, income) on an on-budget credit card, whether created, edited, confirmed from an import (the row is `rejected` with that code and stays staged), recorded from a schedule, or written as a reconciliation adjustment. A categorized inflow on a card (a merchant refund) is not income and stays allowed, and so are a card payment (a transfer, whose legs have no category) and income on an off-budget card. A transfer from an off-budget account into an on-budget card with no category is income on the card too, and is refused the same way, on create, on import and when an edit clears its category (`#598`). The automatic firing of scheduled transactions leaves such a scheduled transaction due and unrecorded, and fires the others.

Before #548 the API accepted such a transaction, and one of them makes every `GET .../budget-months/:month` of its workspace answer 400 `unsupported_transaction`. To find any already stored, run the read-only query in `scripts/dev/find-card-income.sql` as the table owner (it lists transactions and scheduled transactions, across every workspace):

```bash
$ psql "$DATABASE_URL" -f scripts/dev/find-card-income.sql
# or, on a host without psql, through the PostgreSQL container:
$ docker exec -i envelope-postgres-1 psql -U envelope -d envelope < scripts/dev/find-card-income.sql
```

No rows means nothing to fix. No migration changes them, because only the user knows what each one was. Fix each one by hand, through the API or the web app (as a member of the workspace with the `owner` or `editor` role), choosing what it really was:

- A refund of a purchase: give it the category of the original purchase (`PATCH .../accounts/:accountId/transactions/:transactionId` with `splits: [{ "categoryId": "<category>", "amountCents": <amount> }]`, or edit it in the account register).
- Cashback or another inflow with no category of its own: delete it, then record what design.md ("Credit cards") describes for income on a card, an income transaction on a cash account plus a card payment (a transfer from that account to the card) of the same amount.
- A mistake: delete it.

A reconciled transaction must be unlocked first (`POST .../transactions/:transactionId/unlock-reconciliation`). A scheduled transaction the query lists is fixed the same way: give its split a category (`PATCH .../scheduled-transactions/:scheduledTransactionId`), or delete it. Run the query again afterwards: it should list nothing.

### Amounts above the cap stored before #651

Before #651 a single amount could be as large as about 90 trillion; two such amounts make every `GET .../budget-months/:month` of the workspace answer 422 `amount_total_overflow` (before #651, 400 `invalid_amount` with `label` `unassigned`). To find any amount above today's cap already stored, run the read-only query in `scripts/dev/find-amounts-over-cap.sql` as the table owner (it lists transactions, scheduled transactions, assignments, targets, staged import rows and trades, across every workspace; not reconciliations, whose statement balance is not capped):

```bash
$ psql "$DATABASE_URL" -f scripts/dev/find-amounts-over-cap.sql
# or, on a host without psql, through the PostgreSQL container:
$ docker exec -i envelope-postgres-1 psql -U envelope -d envelope < scripts/dev/find-amounts-over-cap.sql
```

No rows means nothing to fix. No migration changes them, and no database constraint refuses them, because only the user knows what each one was: almost always a typing mistake. Fix each one by hand, through the API or the web app, as a member of the workspace with the `owner` or `editor` role: edit the amount to what it should have been (`PATCH` the transaction, scheduled transaction or trade, `PUT` the target), or delete it; an assignment is undone (`POST .../assignments/:entryId/undo`), a staged row rejected. A reconciled transaction must be unlocked first (`POST .../transactions/:transactionId/unlock-reconciliation`). Run the query again afterwards: it should list nothing.

### Currencies mixed before #652

Every account keeps its own currency, and amounts in different currencies are never added together until exchange rates exist (`docs/domain-guide.md`, "Each account in its own currency"). The API refuses an on-budget account, card included, outside the workspace's base currency (400 `account_currency_not_base`) and a transfer between accounts in different currencies (400 `currency_mismatch`; an import row confirmed as one is `rejected` with that code and stays staged). Before #652 it accepted both: an on-budget account's amounts were added to the budget as if they were in the base currency, and a transfer moved the same number of minor units from one currency into another. To find any already stored, run the read-only query in `scripts/dev/find-cross-currency.sql` as the table owner (it lists both, across every workspace, and also any workspace or account whose currency is not three upper-case letters, such as `eur` or `EURO`):

```bash
$ psql "$DATABASE_URL" -f scripts/dev/find-cross-currency.sql
# or, on a host without psql, through the PostgreSQL container:
$ docker exec -i envelope-postgres-1 psql -U envelope -d envelope < scripts/dev/find-cross-currency.sql
```

No rows means nothing to fix. No migration changes them, because only the user knows what each one was:

- A cross-currency transfer (`cross_currency_transfer`): delete it (`DELETE .../accounts/:accountId/transactions/:transactionId` on either leg, or in the account register; a reconciled leg must be unlocked first), then record what really happened as an outflow from one account and an inflow into the other, each in its own currency.
- An on-budget account in another currency (`on_budget_account`): neither its currency nor its on-budget status can be changed through the API. If the currency was a mistake and its amounts really are in the base currency, correct the row as the table owner (`UPDATE accounts SET currency = '<base currency>' WHERE id = '<id>';`). Otherwise create an off-budget account in that currency, record its transactions there, delete them from the on-budget one and close it.
- A malformed currency (`malformed_workspace_currency`, `malformed_account_currency`): neither a workspace's base currency nor an account's currency can be changed through the API. Correct the row as the table owner to the code it was meant to be (`UPDATE workspaces SET base_currency = 'EUR' WHERE id = '<id>';`, `UPDATE accounts SET currency = 'EUR' WHERE id = '<id>';`), keeping every on-budget account in the workspace's base currency. A well-formed code the runtime does not know (`XYZ`, the withdrawn `VEF`) is not listed, since SQL cannot tell it from a real one.

Run the query again afterwards: it should list nothing.

### Codes stored before #711 and #595

Since #711 a workspace's tax country must be an officially assigned ISO 3166-1 alpha-2 code (`@envelope/core`'s `ISO_3166_1_ALPHA2_CODES`), and since #595 an instrument's currency must be an ISO 4217 code the runtime lists as in use (`isKnownCurrency`, the same check as an account's). Both checks apply when the value is written; a row stored before them is read back unchanged, and no migration touches it. To find a workspace holding a tax country outside the list (`ZZ`, `EU`, `UN`…), run the read-only query as the table owner:

```bash
$ psql "$DATABASE_URL" -f scripts/dev/find-unassigned-tax-countries.sql
```

Such a workspace works as one in a country with no tax rules (only `IT` has any today); its owner sets a valid code, or none, with `PATCH /workspaces/:workspaceId`. An instrument quoted in a well-formed code the runtime does not know (`XYZ`) cannot be found in SQL, which has no list of currencies: compare `SELECT DISTINCT currency FROM instruments` with the currencies of the accounts. No account can trade such an instrument (`currency_mismatch`), so it is harmless; correct or delete it as in "Correcting the instruments catalog".

## Things to understand

Comparisons with Perl/CGI/DBI, to find your way around the code.

| In this code | In Perl/CGI/DBI | Note |
| --- | --- | --- |
| `loadConfig()` reading `process.env` | Reading `%ENV` in a CGI script, or a `.ini` parsed by hand | Done once, in one place, with validation, instead of scattered `$ENV{...}` reads |
| `pg.Pool` | `Apache::DBI` or a `DBI->connect_cached` | Keeps a handful of open connections ready, instead of connecting on every request |
| `pool.query("SELECT 1", [...])` with `$1, $2` | `$dbh->prepare("... WHERE id = ?")->execute($id)` | Same idea: parameters are sent separately from the SQL text, never concatenated into it |
| `src/db/migrate.ts` | Running `psql -f change.sql` by hand and noting down which ones you already ran | The runner tracks what has been applied in a table (`schema_migrations`), so it never reapplies or forgets a file; an advisory lock (`pg_advisory_lock`, a named lock like `flock` on a lock file) makes a second runner wait for the first |
| Fastify route handler (`app.get("/health", async (req, reply) => ...)`) | A `mod_perl` handler subroutine, or a CGI script mapped to a URL | Same shape: receives a request, returns a response; Fastify keeps the process running instead of forking per request |
| `app.fastify.inject({ method: "GET", url: "/health" })` in tests | Calling the handler subroutine directly with a fake request, instead of going through Apache | No real socket, so tests are fast and do not need a free port |
| Structured JSON logs (`pino`, built into Fastify) | `Log::Log4perl` with a line-based format, or `warn()` to STDERR | One JSON object per line, with a level and a timestamp, easy to filter and ship to a log collector |
| `process.on("SIGTERM", ...)` | `$SIG{TERM} = sub { ... }` | Same idea: close connections cleanly before the process actually exits |
| `createRemoteJWKSet` + `jwtVerify` (`jose`) | Checking a signed cookie or a Kerberos ticket against a key you fetch once and cache | Keycloak signs the token with a private key only it holds; the API only ever sees the matching public keys, published at a URL, and never has to trust the caller's word for who they are |
| `request.db` held open for the whole request, `onSend` commits it for a reply below 400 and rolls it back otherwise, `onError` rolls it back | `$dbh->begin_work` at the top of a CGI script, `$dbh->commit` at the bottom, `$dbh->rollback` in the `die` handler | One connection, one transaction per request, so every query in that request sees the same `SET LOCAL` session variables |

A request's writes are kept only for a successful reply. Every workspace-scoped request runs in one database transaction, committed only when the reply's status is below 400; any 4xx or 5xx reply, or a thrown error, rolls it back (#515). So a handler can write first and validate afterwards: replying 400 (for example through `sendIfValidationError`), 404 or 409 leaves nothing stored, and a client that retries after an error never creates a duplicate. A write that must survive a failed request (none does today) would have to run in its own, separately committed transaction, stated explicitly in its handler. `withUserScopedTransaction` follows the same rule for the routes outside a workspace: it commits only when its callback returns, so such a handler decides its error replies before writing, or throws.

### Length limits on names and free text

Every create and update route caps the names and free text it accepts (#507), so one member cannot store values close to the 1 MiB request body limit that every other member's lists then carry. The limits are `@envelope/core`'s `MAX_NAME_LENGTH` and `MAX_FREE_TEXT_LENGTH`, counted in Unicode code points (an emoji counts once), after trimming where the route trims:

| Limit | Fields |
| --- | --- |
| 100 (`MAX_NAME_LENGTH`) | Account, category group, category, workspace and portfolio names, on create and rename |
| 500 (`MAX_FREE_TEXT_LENGTH`) | Transaction and transfer `payee` and `memo`, every split's `memo`, the same on scheduled transactions, a portfolio's `purpose`, a reconciliation's `adjustment.memo`, a trade's `memo`, and synced `transactions.payee`/`transactions.memo` changes |

The payee takes the free-text limit, not the name one, because a file import stores a bank's whole description in it. A value over its limit is refused with a 400, `{ "error": "text_too_long", "details": { "field": "<field>", "max": <limit> } }`, where `field` is the body property (`name`, `purpose`, `payee`, `memo`, `splits[1].memo`, `adjustment.memo`) or, for a sync upload, the change's `fieldName`; a sync upload with one such change applies none of the batch, and so does one whose `transactions.payee`/`transactions.memo` change carries anything but a string or `null` (a 400 naming the field). Payees and memos read from an imported file are not checked yet.

### The cap on a single amount

Every amount a request writes is at most `@envelope/core`'s `MAX_AMOUNT_CENTS`, 10^12 minor units either way (€10,000,000,000.00; ADR 0002, #651): a transaction's splits and its own total, a transfer and a transfer leg's edit, an assignment, a credit card's `startingBalanceCents`, a scheduled transaction's splits, a target, each row of an imported file, the adjustment a reconciliation would write, and a trade's gross, fees, taxes, accrued interest, withholdings, cost basis and the cash leg they add up to. An amount above it is refused with a 400, `{ "error": "amount_too_large", "details": { "label": "<which amount>", "max": 1000000000000, "value": "<value>" } }`, and nothing is written. `label` is `amount` for a single amount, `total` for a transaction's splits that add up beyond the cap, `startingBalance`, `adjustment`, or the trade field (`grossCents`, `feesCents`…, `cash` for the cash leg). A staged import row above the cap, from before #651, is rejected at confirmation with that code and stays staged. An amount the API computes itself is never refused: quick assign writes a category's amount above the cap as several entries of at most the cap, in the same batch, so they undo together.

Sums and balances are not capped: a balance or a budget figure can be above €10,000,000,000, and so can an import's `closingBalanceCents` and a reconciliation's `statementBalanceCents`, which are only compared with the account's balance (they must still be safe integers, or the answer is 400 `invalid_amount`). A budget month whose stored amounts add up beyond the safe integer range, which only rows stored before the cap can do, answers 422 `{ "error": "amount_total_overflow", "details": { "label": "transactions", "transactionIds": "<id>,<id>", "count": 2 } }`, naming the transactions above the cap (or the largest ones): `transactionIds` is a comma-separated list of at most 20 ids, and `count` is how many there are in all, so it can be more than the ids listed; when it is the assignments that overflow, `label` is `assignment` with its `month` and `categoryId`. See "Amounts above the cap stored before #651" below.

### Import size limit

`POST /workspaces/:workspaceId/accounts/:accountId/import` accepts a JSON body of at most 1 MiB (1,048,576 bytes), the file's text included (`IMPORT_BODY_LIMIT_BYTES`, `src/routes/import.ts`, #675). A larger body answers 413 before anything is parsed or written. The route states the limit itself, rather than relying on Fastify's global default (also 1 MiB), so the limit on a statement upload stays this one if the server's default ever changes. A larger statement is imported in several smaller files, for example one per month. The price file import (`POST /workspaces/:workspaceId/instruments/:instrumentId/prices/import`, #83) has the same limit on its `text/csv` body, and at most 20,000 rows.

Every parser behind the route (`@envelope/core`'s CSV, OFX, QIF and CAMT.053) takes time linear in the file's size, whatever the file holds, so a body within the limit cannot hold the server's event loop for long: before #675, an OFX file of opening tags that never close (`"<STMTTRN>".repeat(110000)`, about 1 MB) kept every workspace's requests waiting for close to a minute.

### Error replies

A route checks every id it takes from the request before writing with it (#512). An account id, in the path (`/accounts/:accountId/…`: import, staging, reconciliation, creating and listing transactions) or in the body (`accountId` of a new scheduled transaction), must name an account of the selected workspace, or the route answers 404 `{ "error": "account not found" }` and writes nothing, the same for an account of another workspace as for one that does not exist. A malformed `…Id` path parameter answers 404 too, without reaching the database (`src/ids.ts`); a malformed workspace id answers 403, like any workspace the caller is not a member of. Malformed ids inside a body are answered by the route itself: a transfer's account as `unknown_account`, a staged row in a confirmation as `not_found`.

Anything a route does not answer itself goes through one global error handler (`src/errors.ts`), which never sends an error's own message: a database message names tables and constraints, and two different database errors for the same request could tell a caller whether another workspace holds a row with a given id. A 500 logs the full error server-side instead, at `error` level, with a database error's `detail` redacted (for a CHECK or NOT NULL failure it holds the whole row). A mapped client error logs only its `code` and status at `info`, since a JSON parse error or an invalid-input message quotes the request's own data; a permission or Row-Level Security refusal from the database logs at `warn`, so a missing grant does not go unnoticed. The request's transaction is rolled back whatever the reply.

| Error | Status | Body |
| --- | --- | --- |
| A `ValidationError` not already answered by its route | 400 | `{ "error": "<code>", "details": { … } }` |
| A `ValidationError` with the code `amount_total_overflow` (#651) | 422 | `{ "error": "amount_total_overflow", "details": { "label", … } }`: from a budget month, `label` `transactions` with `transactionIds` (comma-separated, at most 20) and `count` (all of them), or `label` `assignment` with `month` and `categoryId`; from positions, `label` the total and `tradeId` the trade being replayed |
| PostgreSQL foreign-key violation (23503) | 400 | `{ "error": "invalid_reference" }` |
| PostgreSQL invalid input syntax (22P02) | 400 | `{ "error": "invalid_input" }` |
| PostgreSQL invalid date or time (22007, 22008): a date a route did not check first, such as `2026-02-30` (#655) | 400 | `{ "error": "invalid_date" }` |
| PostgreSQL insufficient privilege (42501), a Row-Level Security refusal included | 403 | `{ "error": "forbidden" }` |
| A write to a closed account, refused by migration 0033's trigger (23514, constraint `account_closed`; #729, or, for a trade or an edited transaction, by `AccountClosedError` before the position replay or any other check, #741, #655; [ADR 0018](../../docs/adr/0018-closed-accounts-enforced-in-the-database.md)): a transaction, split, transfer leg, trade (a split of an instrument the account held on its date included), cash leg, scheduled transaction or its splits (created, edited, skipped, recorded or deleted), reconciliation or unlock, an import confirmation into it | 409 | `{ "error": "account_closed" }` |
| A client error Fastify raises itself (a malformed JSON body, an unsupported content type, a body too large) | Its own 4xx | `{ "error": "bad_request" }`, `"unsupported_media_type"`, `"payload_too_large"` and so on, with Fastify's own `code` (`FST_…`) when it has one |
| An `Idempotency-Key` used for a different request, or a `batchId` used for other entries (see "Idempotent creates" below) | 409 | `{ "error": "id_conflict", "details": { "field": "Idempotency-Key" } }`, or `{ "field": "batchId", "batchId" }` |
| The same key or batch id still held by a request in flight after 5 seconds | 409 | `{ "error": "request_in_progress", "details": { "retryAfterSeconds": 1 } }`, with `Retry-After` |
| A request over a rate limit (see "Rate limits" below) | 429 | `{ "error": "too_many_requests", "details": { "retryAfterSeconds": <n> } }`, with `Retry-After` |
| Anything else | 500 | `{ "error": "internal_error" }` |

### Idempotent creates

A client that retries a create after a timeout sends the same `Idempotency-Key` header (a UUID) again, and the create is recorded once (#559, [ADR 0020](../../docs/adr/0020-idempotent-creates.md)). The routes that take it: `POST .../accounts/:accountId/transactions`, `POST .../transfers`, `POST .../assignments`, `POST .../quick-assign`, `POST .../scheduled-transactions/:scheduledTransactionId/record`, `POST .../assignment-batches/:batchId/undo` and `POST .../assignments/:entryId/undo`.

- The key is kept per workspace, with a fingerprint of the request (method, route, path ids, query, the body with its keys sorted, the member) and the reply. The same key and request get the stored status and body again, with `Idempotent-Replayed: true`, and nothing is written, audited or queued; this holds even when the state changed since (the transaction deleted, a category removed), since the replay comes before validation. Another body, route, account or member under the key is 409 `id_conflict` (`details.field: "Idempotency-Key"`). The same key in another workspace is a new key there.
- Only a success is kept: a 4xx or 5xx rolls the request back, key included, so a corrected request can be retried under the same key.
- A key that is not one UUID (a repeated header included) is 400 `invalid_field` (`details.field: "Idempotency-Key"`); so is the header on any other `POST`, `PUT`, `PATCH` or `DELETE`, which does not take it. `GET` ignores it. A body nested more than 32 levels deep, or with a number JSON reads as infinite, is 400 `invalid_body` under a key.
- **Lifetime: 24 hours.** The hourly `idempotency-keys-sweep` job deletes older keys, so a stored reply lives about 25 hours; a key sent again after its lifetime counts as new.
- **Order and locks.** Authentication, membership, write role and the path's own account come first; then the key, the request's first lock; then a client `batchId`; then everything else (the category-month locks, #704; transactions `FOR UPDATE` in id order, #554). A duplicate sent while the first request is still running waits on its key and then replays its reply; after 5 seconds it gets 409 `request_in_progress` with `Retry-After`.
- **Adding a route:** `config: IDEMPOTENT_ROUTE` in its options, its handler wrapped in `withIdempotencyKey`, and its success sent through `sendAndRemember`. A success sent any other way under a key fails with 500, and migration 0039's deferred trigger refuses to commit a key without its reply. Trades keep `id_taken` for a repeated client id (ADR 0012) until 0.4.2.

### Rate limits

The API limits requests in process, with `@fastify/rate-limit` and its in-memory store (#566, [ADR 0017](../../docs/adr/0017-api-rate-limiting.md)), in two layers:

- **Per client address**, on `onRequest`, before anything else: every route counts, the health check and requests with a bad or missing token included, so neither can load the database or the token verifier without limit. The address is the connection's own, unless the connection comes from a proxy listed in `TRUST_PROXY`, whose `X-Forwarded-For` is then believed; an IPv6 address counts by its /64.
- **Per user**, right after the user mapper, keyed on the user the token verified, never on a claim of a token not yet verified: every request, then writes, then file imports, each against its own limit, so one member's requests never use up another's. A request without a valid token is answered 401 before it reaches this layer.

The defaults are set in one place, `RATE_LIMIT_DEFAULTS` in `src/config.ts`. An ordinary session in the web app with a 35-category budget sends about 325 requests in 7 seconds, so a user gets 1200 a minute. The per-address limit (2400) is kept above the per-user one: one address can carry several members (a household behind one NAT, or everyone under Caddy's address when `TRUST_PROXY` is not set), and since it runs first, a lower one would refuse a member before the per-user limit applies. Each of the four limiters keeps its own in-memory store of at most 10 000 keys.

A CORS preflight (`OPTIONS`) is answered by `@fastify/cors` before the per-address limit and never counted; the CORS policy exposes `Retry-After` so the web app can read it, and `Idempotent-Replayed` (#559). Sign-in is not limited here: the API has no sign-in route, and Keycloak's own brute-force detection limits failed sign-in attempts.

A request over a limit is answered 429 `too_many_requests` with `Retry-After` (in seconds) and `details.retryAfterSeconds`; the web app shows the code's translation. The counters reset when the process restarts, and they are per process: running more than one API process would need a shared store. The limits are in "Configuration" above; the tests build apps with limits far above what they send (`src/test-helpers/rate-limits.ts`), except `src/rate-limit.test.ts`, which tests the limits themselves.
