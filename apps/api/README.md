# @envelope/api

The backend server: a Fastify HTTP API on top of PostgreSQL. Steps 1 to 4 of the backend MVP (see `CLAUDE.md`) are done: configuration, a database pool, a migration runner, the domain schema and Row-Level Security per workspace, and authentication — Keycloak access tokens verified against the realm's JWKS, mapped to a local `users` row, workspace membership checked with the request's Row-Level Security session variables set. Token verification and user mapping are global preHandlers, applied to every route except `/health`; workspace membership stays an explicit per-route opt-in. Step 4, the Budget API: accounts, with their payment category and optional starting balance for on-budget credit cards; category groups and categories, sortable and archivable; transactions, with splits, income, reconciliation locking and transfers between accounts; the assignment ledger, an append-only record of assign/unassign/move money, with undo; the budget month itself, computed by `@envelope/core` from all of the above, plus its own list of unresolved problems, derived from that same computation; goals (targets), one per category, joined with how much each still needs this month; days of buffer, recomputed from real transactions; quick assign, funding a whole scope of categories in one ledger batch; scheduled transactions (rent, salary, subscriptions), reserving money in their category ahead of being recorded, now firing automatically on their own due date (#38). Every endpoint that changes budget data rejects a `read_only` member; `owner` and `editor` can write, everyone can read. Step 5 (Import) has started: CSV files, given a column mapping remembered per account, and OFX, QIF and CAMT.053 statement downloads, self-describing and needing no mapping, are staged with duplicate detection against the account's existing transactions before being confirmed into real transactions. Reconciliation ties a statement's closing balance to the cleared transactions up to that date, resolving a real leftover difference with an adjustment transaction; unlocking a reconciled transaction is a separate, audited action. Step 6 (Queue and notifications) has started: a `QueueDriver` interface (`enqueue`, `schedule`, `work`) behind which the rest of the code never sees pg-boss directly, now wired into `main.ts` and creating a transaction or a transfer, which queues a `budget-recompute` job in the same database transaction as the write that triggers it. Every job delivery is idempotent by construction: `processed_jobs` discards a repeat before its handler ever runs. Push notification delivery has one interface and, for now, one real adapter — Web Push, keyed by the triggering job's id so a duplicate delivery coalesces on the device instead of showing twice; APNs and Android/FCM are stubs until the mobile app (0.3.0) gives them a real device to send to. The `budget-recompute` job now runs for real: it notifies every workspace member when a category goes negative, a purchase exceeds the available balance, or money arrives to assign, but only when that problem is new or its amount has changed since the last time. Step 7 (Sync) is done for its own milestone's scope (`transactions.memo`/`transactions.payee`; every other field and entity is added only once something needs to sync it): `change_log`, one row per field-level change (entity id, field name, hybrid logical clock, device id, value), idempotent on the change's own id so a repeated network retry never duplicates a record; `POST /workspaces/:workspaceId/changes` applies a device's own queued changes by clock alone, converging to the same result whatever order they arrive in, rejecting one against a reconciled transaction outright; `GET /workspaces/:workspaceId/changes` is the download side, every change later than the clock a device last saw. Certified end to end by a real two-device smoke test: offline edits, including a genuine conflict, converge to the same result on both sides with nothing lost or duplicated.

| `src/notifications/repository.ts` | `sendPushToUser`: dispatches to every one of a user's registered devices (`device_tokens`), recording each as a `notification_deliveries` row; a device already marked `sent` for a given job is never delivered to again, so a retry resumes only from the still-pending ones. `registerDeviceToken`/`removeDeviceToken` (#61) are the opt-in/opt-out side, idempotent inserts/deletes through the same `set_config('app.user_id', ...)` convention `listWorkspacesForUser` already established for a route with no workspace of its own |
| `src/notifications/index.ts` | `createPushDrivers(config)`: assembles the three platform drivers behind `PushDrivers` |
| `src/notifications/notified-problems.ts` | `reconcileNotifiedProblems`: compares a workspace/month's current budget problems against `notified_budget_problems`, returns only the new-or-changed ones, and overwrites that state to match (a resolved problem is deleted, so it counts as new again if it reappears) — find-then-write, not a DB unique constraint (a nullable `category_id`) (#40) |
| `src/notifications/budget-alert-text.ts` | `composeBudgetAlert`: renders a push notification's title/body for a set of budget problems, from a small, self-contained English/Italian lookup local to this package (no i18n catalog infrastructure exists yet; that's chosen in "phase 1"), picked by the recipient's own `language`, amounts formatted in their own `locale` (#40) |
| `src/notifications/budget-recompute-job.ts` | `createBudgetRecomputeHandler(drivers)`: the `budget-recompute` job's handler — recomputes a workspace/month's budget problems, reconciles them against the last-known state, and notifies every workspace member (regardless of role) whose problem is new or changed (#40) |
| `src/memberships/repository.ts` | `listWorkspaceMembers`: every member of a workspace regardless of role, with their own `language`/`locale`, for the budget-recompute job to notify (#40); `listWorkspacesForUser` (#50): every workspace a user belongs to, with its `baseCurrency` (#51) and `timeZone` (#326), opening its own short transaction with only `app.user_id` set (migration 0022's own RLS allowance on `workspaces`, mirroring `memberships`' from migration 0008) |
| `src/sync/repository.ts` | `recordChange`/`getLatestChange`: the field-level change log (design.md, "Field-level change protocol"). `recordChange` is idempotent on the change's own id (`ON CONFLICT (id) DO NOTHING`) — a repeated network retry of the same change never creates a duplicate row (#42). `listChangesSince`: every change later than a given HLC (or all of them, for a first sync), ordered the same way `compareHlc` would via Postgres's own row comparison `(hlc_physical, hlc_counter, device_id) > (...)` (#44) |
| `src/sync/apply.ts` | `applyIncomingChange`: records an incoming change, then writes it onto the real column an explicit allowlist maps its `field_name` to — but only if its HLC is later than the field's current one; the allowlist exists because `field_name` comes from the device, not from code we wrote, and building `UPDATE` SQL from it directly would let an untrusted string name any column. Scoped to `transactions.memo`/`transactions.payee` for now (#43). A change to a reconciled transaction is rejected outright (`"locked"`), checked before clock resolution even runs and never recorded, so a retry after the transaction unlocks (#32) is unaffected by the rejected attempt (#45) |
| `src/routes/sync.ts` | `POST /workspaces/:workspaceId/changes`: the upload side of the sync protocol — a device's own queued changes, applied in any order with the same converged result (#43). `GET /workspaces/:workspaceId/changes?sincePhysical=&sinceCounter=&sinceDeviceId=`: the download side — every change later than that HLC, or all of them when the three query params are omitted; any read-only member can call it too, unlike the upload side (#44) |
| `src/test-helpers/keycloak.ts` | Provisions a throwaway Keycloak realm, clients and user for tests, through the admin REST API |
| `src/test-helpers/app-role.ts` | Grants `envelope_app` a test-only login (idempotently, cluster-wide) so tests can connect as the same restricted role the running server uses |
| `src/test-helpers/queue-role.ts` | Same as `app-role.ts`, for `envelope_queue` |
| `src/test-helpers/vapid-keys.ts` | A fixed, throwaway VAPID key pair so tests can start the server without a real one (#39/#40) |
| `src/app.ts` | `buildApp(config, queue?)`: assembles the Fastify instance and its routes, without opening a port (used directly by tests, which mostly omit `queue`); `queue`, when given, is threaded into the transactions routes so a write can enqueue a job in its own transaction (#35) |
| `src/main.ts` | Entry point: loads the config, creates and starts the queue driver (its own pool, separate from `buildApp`'s), registers the `budget-recompute` handler (#40) and schedules/registers the `scheduled-transactions-fire` one (#38, an hourly cron — frequent enough to catch every workspace's own local midnight, whatever its time zone), builds the app (passing its own VAPID public key, #61), starts listening; stops the app, the queue driver and its pool on shutdown |
| `*.test.ts` | Tests, next to the file they check |

## Configuration

Copy `.env.example` to `.env` and adjust it; `.env` is read automatically by `dev`/`start`/`migrate` and is ignored by Git.

| Variable | Default | Meaning |
| --- | --- | --- |
| `DATABASE_URL` | — (required by `migrate`) | The migration runner's connection: needs DDL privileges, so it's the superuser (`envelope`) |
| `APP_DATABASE_URL` | — (required by `dev`/`start`) | The running server's own connection: `envelope_app`, restricted by Row-Level Security (ADR 0006) |
| `QUEUE_DRIVER` | `postgres` | Selects the queue adapter (design.md, "Queue module"); `postgres` (pg-boss) is the only one so far. Read by `loadQueueConfig`, a second, separate config loader (below) |
| `QUEUE_DATABASE_URL` | — (required by `dev`/`start`) | The queue module's own connection: `envelope_queue`, which pg-boss uses to manage its own schema (#34) |
| `VAPID_SUBJECT` / `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` | — (required by `dev`/`start`) | VAPID credentials for the `web` push adapter (#39), read by `loadPushConfig`, a third, separate config loader; required to start the server now that the `budget-recompute` job (#40) can send through it. Generate with `npx web-push generate-vapid-keys`. Self-hosting how-to: `#41` |
| `KEYCLOAK_ISSUER` | — (required) | The realm's issuer URL, e.g. `http://127.0.0.1:8080/realms/envelope`; also where the JWKS is fetched from |
| `KEYCLOAK_AUDIENCE` | — (required) | The client id every access token must be issued for |
| `HOST` | `127.0.0.1` | Address the server listens on |
| `PORT` | `3000` | Port the server listens on |
| `LOG_LEVEL` | `info` | `fatal`, `error`, `warn`, `info`, `debug` or `trace` |
| `LOG_PRETTY` | `false` | Human-readable logs instead of JSON; only for a terminal, never in production |
| `NODE_ENV` | `development` | |

A missing or invalid variable makes the process exit immediately with a clear error, instead of failing later somewhere unrelated. `DATABASE_URL` and `APP_DATABASE_URL` are two different connections on purpose (ADR 0006): the first can create tables, the second cannot even see another workspace's rows. `QUEUE_DRIVER`/`QUEUE_DATABASE_URL` are validated by their own loader, `loadQueueConfig` (`src/config.ts`), kept separate from `Config`/`loadConfig` so the many existing tests that build an app without a queue stay untouched (#34).

### Giving `envelope_app` (and `envelope_queue`) a login

Migrations create the `envelope_app` and `envelope_queue` roles but deliberately never give them `LOGIN` or a password (ADR 0006: that would mean committing a real credential to the repository). Do it once per Postgres instance, the same way `infra/.env` already holds the `envelope` and Keycloak passwords:

```bash
$ docker exec -it envelope-postgres-1 psql -U envelope -d envelope \
  -c "ALTER ROLE envelope_app WITH LOGIN PASSWORD '<a password you pick>';" \
  -c "ALTER ROLE envelope_queue WITH LOGIN PASSWORD '<a different password you pick>';"
```

Roles are shared by the whole Postgres instance (not per database), so this one command covers both the `envelope` and `envelope_test` databases. Use those passwords in `APP_DATABASE_URL` and `QUEUE_DATABASE_URL`.

## Running the integration tests locally

The tests need their own database, separate from the one used for everyday development, so a broken test never touches real data. They also need `KEYCLOAK_ADMIN_PASSWORD` (the value from `infra/.env`): the Keycloak tests provision and tear down their own realm through the admin API, so no manual realm setup is needed to run them.

```bash
$ createdb -h 127.0.0.1 -U envelope envelope_test   # once, asks for the password in infra/.env
$ DATABASE_URL=postgres://envelope:<password>@127.0.0.1:5432/envelope_test \
  KEYCLOAK_ADMIN_PASSWORD=<password from infra/.env> \
  pnpm --filter @envelope/api test
```

CI does the same against a fresh PostgreSQL service container and a Keycloak container it starts and waits on: see `.github/workflows/ci.yml`.

## Administration

### Correcting the instruments catalog

The API never updates or deletes an instrument (#76): other workspaces may already reference it, and `envelope_app` has only `SELECT` and `INSERT` on `instruments`. An administrator corrects or removes a bad catalog row with SQL, connected as the table owner (the `envelope` role that runs the migrations, `DATABASE_URL`), never as `envelope_app`:

```bash
$ psql "$DATABASE_URL"
envelope=# SELECT id, isin, ticker, exchange, name, type, currency, price_factor_e6 FROM instruments WHERE isin = 'XS0000000000';
envelope=# UPDATE instruments SET name = 'Corrected name' WHERE id = '<id>';
envelope=# DELETE FROM instruments WHERE id = '<id>';
```

Check before a correction that it keeps every workspace's figures right: changing `type`, `currency` or `price_factor_e6` changes how every holding of that instrument is valued and taxed, in every workspace. Once trades reference instruments (#77), a row that is still referenced cannot be deleted; correct it in place instead.

## Things to understand

Comparisons with Perl/CGI/DBI, to find your way around the code.

| In this code | In Perl/CGI/DBI | Note |
| --- | --- | --- |
| `loadConfig()` reading `process.env` | Reading `%ENV` in a CGI script, or a `.ini` parsed by hand | Done once, in one place, with validation, instead of scattered `$ENV{...}` reads |
| `pg.Pool` | `Apache::DBI` or a `DBI->connect_cached` | Keeps a handful of open connections ready, instead of connecting on every request |
| `pool.query("SELECT 1", [...])` with `$1, $2` | `$dbh->prepare("... WHERE id = ?")->execute($id)` | Same idea: parameters are sent separately from the SQL text, never concatenated into it |
| `src/db/migrate.ts` | Running `psql -f change.sql` by hand and noting down which ones you already ran | The runner tracks what has been applied in a table (`schema_migrations`), so it never reapplies or forgets a file |
| Fastify route handler (`app.get("/health", async (req, reply) => ...)`) | A `mod_perl` handler subroutine, or a CGI script mapped to a URL | Same shape: receives a request, returns a response; Fastify keeps the process running instead of forking per request |
| `app.fastify.inject({ method: "GET", url: "/health" })` in tests | Calling the handler subroutine directly with a fake request, instead of going through Apache | No real socket, so tests are fast and do not need a free port |
| Structured JSON logs (`pino`, built into Fastify) | `Log::Log4perl` with a line-based format, or `warn()` to STDERR | One JSON object per line, with a level and a timestamp, easy to filter and ship to a log collector |
| `process.on("SIGTERM", ...)` | `$SIG{TERM} = sub { ... }` | Same idea: close connections cleanly before the process actually exits |
| `createRemoteJWKSet` + `jwtVerify` (`jose`) | Checking a signed cookie or a Kerberos ticket against a key you fetch once and cache | Keycloak signs the token with a private key only it holds; the API only ever sees the matching public keys, published at a URL, and never has to trust the caller's word for who they are |
| `request.db` held open for the whole request, `onSend` commits it for a reply below 400 and rolls it back otherwise, `onError` rolls it back | `$dbh->begin_work` at the top of a CGI script, `$dbh->commit` at the bottom, `$dbh->rollback` in the `die` handler | One connection, one transaction per request, so every query in that request sees the same `SET LOCAL` session variables |

A request's writes are kept only for a successful reply. Every workspace-scoped request runs in one database transaction, committed only when the reply's status is below 400; any 4xx or 5xx reply, or a thrown error, rolls it back (#515). So a handler can write first and validate afterwards: replying 400 (for example through `sendIfValidationError`), 404 or 409 leaves nothing stored, and a client that retries after an error never creates a duplicate. A write that must survive a failed request (none does today) would have to run in its own, separately committed transaction, stated explicitly in its handler. `withUserScopedTransaction` follows the same rule for the routes outside a workspace: it commits only when its callback returns, so such a handler decides its error replies before writing, or throws.

### Length limits on names and free text

Every create and update route caps the names and free text it accepts (#507), so one member cannot store values close to the 1 MiB request body limit that every other member's lists then carry. The limits are `@envelope/core`'s `MAX_NAME_LENGTH` and `MAX_FREE_TEXT_LENGTH`, counted in Unicode code points (an emoji counts once), after trimming where the route trims:

| Limit | Fields |
| --- | --- |
| 100 (`MAX_NAME_LENGTH`) | Account, category group, category, workspace and portfolio names, on create and rename |
| 500 (`MAX_FREE_TEXT_LENGTH`) | Transaction and transfer `payee` and `memo`, every split's `memo`, the same on scheduled transactions, a portfolio's `purpose`, a reconciliation's `adjustment.memo`, and synced `transactions.payee`/`transactions.memo` changes |

The payee takes the free-text limit, not the name one, because a file import stores a bank's whole description in it. A value over its limit is refused with a 400, `{ "error": "text_too_long", "details": { "field": "<field>", "max": <limit> } }`, where `field` is the body property (`name`, `purpose`, `payee`, `memo`, `splits[1].memo`, `adjustment.memo`) or, for a sync upload, the change's `fieldName`; a sync upload with one such change applies none of the batch, and so does one whose `transactions.payee`/`transactions.memo` change carries anything but a string or `null` (a 400 naming the field). Payees and memos read from an imported file are not checked yet.

## Current limitations

Step 4 (Budget API) covers a full budget month driven through the API alone, including scheduled transactions (`#22`): created, listed, updated, deleted and recorded/skipped by hand, or fired automatically on their own due date (`#38`). Step 5 (Import) has CSV, OFX, QIF, CAMT.053 import and staging, and reconciliation; payee/category suggestion from the user's rules and history is out of scope for now (`#122`, a later phase). Step 6 (Queue and notifications) has the `QueueDriver` interface and its `postgres` adapter (`#34`), the outbox wired into the transaction-writing code path (`#35`), the idempotent `processed_jobs` register (`#36`), push notification delivery (`#39`) — `web` for real, `ios`/`android` deferred to milestone 0.3.0 — the `budget-recompute` job itself, notifying members only on a new or changed problem (`#40`), the shared double-delivery test harness (`#37`), a periodic job materializing an overdue scheduled transaction in every workspace, each in its own time zone (`#38`; ADR 0010's own `app_is_system_job()` is what lets it enumerate every workspace at all — the two existing RLS allowances both still need a request's own `app.user_id`/`app.workspace_id`, which a cron-triggered job genuinely has neither of), and the Web Push opt-in/opt-out itself (`#61`) — a browser can now actually register for the alerts `#40` already sends, rather than only a test inserting a `device_tokens` row by hand. Step 7 (Sync) has the change record model (`#42`), applying incoming changes by clock (`#43`), the changes-since-clock download endpoint (`#44`), the reconciled-transaction lock at the field-change layer (`#45`) and the milestone's own two-devices-converge smoke test (`#46`), scoped to `transactions.memo`/`transactions.payee` — every other field and entity is added only once something needs to sync it. Not here yet, its own later step of the roadmap: the web app itself (0.1.7 onward) — this package is the API only.
