# apps/web

The web app: a Vite + React PWA that talks to `apps/api` over a real HTTP connection. Step 1, the installable shell (`#48`); step 2, sign-in (`#49`): Authorization Code + PKCE against Keycloak through `react-oidc-context`/`oidc-client-ts`, session handling (the user's own storage, refreshed automatically) and sign-out; step 3, the workspace switcher (`#50`); step 4, the accounts screen (`#51`); step 5, categories and groups (`#52`); step 6, the budget month itself (`#53`); step 7, the account register (`#54`); step 8, quick assign and targets (`#55`). Steps 3–8 were first built against an older sidebar-based visual design; `#323` re-skinned the foundations (see below) to the one `docs/design.md`'s "User interface" now describes, and later issues (`#324` onward) carry the same redesign through the rest of the app.

`#323`, the mariner band foundations: `AppLayout` wraps every screen under `/:workspaceId` in the band `docs/design.md` describes (wordmark, primary navigation as rounded tabs, workspace switcher, user menu) — no sidebar, no account ledger outside the Accounts screen. The shared `SideSheet` component (`src/layout/`) is the one side sheet every form/detail in the app opens in. Self-hosted Bricolage Grotesque and Figtree (both SIL OFL 1.1, `@fontsource-variable/*`) replace the old Archivo/system-ui stack. Editing an assigned amount, moving money, the card-debt detail, scheduled reservations, days of buffer and the budget month's own bars/timeline/"To do" are later issues (`#324`–`#331`, now mostly built — see below) layered onto the budget screen; this issue does not touch its table yet.

`#324`, category bars: the budget month's old assigned/activity/available table is gone, replaced by `@envelope/core`'s `computeCategoryBar`/`computePaymentCategoryBar` and `Bar.tsx` (`docs/design.md`'s "Bars"), grouped, each with a spent line and its available amount styled by state; the band's own second line (month navigation, "Unassigned", the facts row), left inline in `BudgetScreen.tsx` by `#323`, now portals into `AppLayout`'s own band (`useBandSecondRow`). The timeline and "To do" list next to the bars are `#326`; a row's own detail and the group summary side sheet are `#327`.

`#326`, the timeline and "To do" list: above the bars, `@envelope/core`'s `computeTimeline`/`computeTodos` (design.md's "Timeline"/"To do"), rendered by `Timeline.tsx`/`Todo.tsx` from the month's own events (`GET .../budget-months/:month/events`, `#325`/`#346`) and each category's own target progress. Replaces the old one-line notices (`#61`). Not yet interactive: opening a category's own row (`#327`), recording a scheduled transaction (`#330`) and funding an arbitrary subset of categories' targets have no destination to open into yet, so each "To do" row is informational only. The "To do" list shows as soon as the budget month itself does — only its overdue-scheduled entries (and the timeline, which has nothing else to show) wait on the events fetch, so the rest of the list is never held up by it, or hidden just because it failed. Hidden below 600px (a compact rendering of its own is `#331`'s job): `useBudgetMonthEvents` resets to `loading` on every workspace/month change, so a stale month's events are never drawn against the new month's own "today" line. "Today" and "this month" are computed in the workspace's own time zone (`workspaceDate.ts`, fed by `GET /me/workspaces`'s new `timeZone` field, `#326`) — not the browser's, which can disagree with it — the same shared function the account register's own "Today" day heading now also uses, replacing its own separate copy.

`#327`, a category's own row detail: an ordinary category's `.brow` is now a real `<button aria-expanded>` opening `RowDetail.tsx` underneath it, a sibling region (not a side panel), with "Assigned this month" editable in place — typing a value, or `+20`/`-15` for a change, Enter (or leaving the field) commits it as one entry via the existing assignment ledger endpoint (`budget/api.ts`'s new `createAssignments`); Esc reverts without committing. A payment category's row stays a plain, non-interactive `<div>` at this point — its own detail is `#329`. `TargetsPanel.tsx`, `QuickAssignPanel.tsx` and `TargetEditor.tsx` (built in `#55`) move onto the shared `SideSheet` (`#323`) in the same issue: markup and CSS only, their behaviour is unchanged.

`#328`, the "Assign / Move money" side sheet: `MoveMoneyForm.tsx`, one form for both — From (unassigned money or a category with money), To (a category, or unassigned money when moving from a category), the month (this one or one of the next two, only when assigning from unassigned money), amount, and a live preview of both sides before/after, including whether the destination's overspending, reservation shortfall or card debt (`@envelope/core`'s new `amountNeededToCover`) gets covered. One ledger entry, the same `createAssignments` endpoint `#327`'s row-detail editing already uses. "Assign" in the band's unassigned-money box opens it from unassigned money; "Move money" in a category's own row (`RowDetail.tsx`) preselects it as the destination and the amount it is missing, auto-picking a source category when unassigned money alone cannot cover it.

`#329`, a card's own payment category detail: its row becomes clickable too, opening `PaymentCategoryDetail.tsx` — money set aside, a sentence about the card's debt, and (only when any of it is uncovered) the debt meter itself (card balance, set aside, to cover) with "Assign €X from unassigned money" (`MoveMoneyForm`'s new `assignTo` initial: the source is always unassigned money, never auto-swapped for another category) and "Move money here" (the existing `moveTo` initial, same as an ordinary category's own "Move money"). The mockup's own two more specific sentences (the starting balance's own amount and date, or the exact categories whose card spending caused the debt) need data the budget-month API does not expose yet with more than one credit card in a workspace — a generic sentence stands in for both until `#355` adds it.

`#330`, the "Scheduled" side sheet: `ScheduledPanel.tsx` — money reserved this month, "To record" (overdue) and "By the end of the month" groups, each item with Record and Skip, a preview of next month's own reservations against each category's own target ("within the target", "the target asks €X: €Y missing", or "no target" with "Use as target"), and "+ New scheduled transaction". `apps/api` gains `POST .../scheduled-transactions/:id/record`\|`/skip` (not composed client-side: every write request already runs inside one database transaction, so one route handler creating the real transaction and advancing `nextDueDate` together needs no new domain concept) and `@envelope/core` gains `advanceDate`, the calendar-aware recurrence step both actions share. Scheduled income has no backend support yet (`#347`): every scheduled transaction is a single-category expense, the mockup's own "Expected income" group and income/expense toggle are left out until then.

`#217`, a category's own reservation line and a target from a new schedule: once a row opened its own detail (`#327`) and the budget month had its own scheduled-transactions fetch (`#330`), its remaining two acceptance criteria were straightforward — a category row's own reservation clock line (`ReservationLine` in `BudgetScreen.tsx`, `@envelope/core`'s own `reservationShortfall` exported directly for it) and "+ New scheduled transaction"'s own "Use it as this category's target" checkbox.

`#344`, days of buffer in the band: the facts row's own third fact, next to money reserved for scheduled transactions and already assigned to future months — `useDaysOfBuffer.ts` fetches the existing `GET /workspaces/:workspaceId/days-of-buffer` endpoint, rounded for display; no new `packages/core` function needed, since there is no geometry to compute, just a number.

`#343`, the last-used workspace: "/" now also tries the last workspace this browser remembers for the signed-in person (`lastUsedWorkspace.ts`, keyed by the access token's own `sub` claim) before falling back to the existing rules — the only workspace, or `WorkspacePicker`. Picking one from `WorkspacePicker`, or switching from the band's own `WorkspaceSwitcher`, both update the stored preference; a workspace it names but the user can no longer reach is forgotten rather than erroring. No schema or API change — entirely a browser-side preference, never synced across devices.

`#332`, sign-in and the workspace switcher to the new tokens: re-skin, no behavior change. `CenteredCard.tsx`/`.css` (`src/layout/`) factors the full-viewport, centered card `SignIn.tsx` and `WorkspaceGate.tsx`/`WorkspacePicker.tsx` each used to duplicate almost identically (`.sign-in-card`/`.workspace-card`) — one shared component, matching `docs/ux/mockups/sign-in.html`'s own `.card` precisely (a bordered, padded box on the `--desk` background, not bare centered text; the wordmark's own `font-stretch: 75%`; the error state's warning-triangle icon). `WorkspaceSwitcher.css`'s own popover now matches `docs/ux/mockups/settings-first-run.html`'s `.menu-pop` precisely too: `--pen-soft` on hover (was `--desk`), the section label in small caps with letter-spacing, a softer rule before "Workspace settings" (`--rule-soft`), no border-radius.

`#333`, the Accounts screen and the account register to the new tokens. `AccountsScreen.tsx`/`.css`, the one part of this pair `#348` had not already redesigned, gets the same display-face `<h1>` (`font-stretch: 88%`, matching the budget month's own heading) and, new, each open and closed account's own balance (`useAccountBalances.ts`: one `listTransactionsForAccount` fetch per account run in parallel, summed the same way the register itself computes its own total — there is no bulk balance endpoint, and no reason to add one yet) — design.md's own "Accounts and their balances live on the Accounts screen" asked for this, not yet built until now. Below 600px (`usePhoneWidth`) the list becomes the mockup's own `.ph-acc` rows (name, a secondary "type · on/off budget" line, balance right-aligned), closed accounts rendered `.ph-acc.static`, read-only. `TransactionForm.tsx` moves off its own hand-rolled `.side-sheet` markup onto the shared `SideSheet` component (`#323`) — the last caller still duplicating it — and `TransactionForm.css` gains the `.two` grid rule the Date/Amount row needed but never had (copied from the mockup, not previously ported). `AccountRegisterScreen.tsx`'s own reconciled-transaction read-only view makes the same move. `docs/design.md` is corrected to match the register's own already-shipped layout (`#323` removed its sidebar account list in favor of this screen; the prose describing "the account register keeps its list of accounts as its own first column" was never updated when that shipped) — `docs/ux/mockups/account-register.html`'s desktop view still draws that retired sidebar; left as a known, out-of-scope divergence rather than redrawn here.

`#349`, phone polish for the accounts list and register, a follow-up of `#333`'s own review round: the register's phone list was reading the band's own muted text colour on its payee (`rgb(180, 200, 221)`, ~2:1 against the page) instead of `--ink` — both the band's "Demo User" label and this list's own payee wrapper used the class name `.who`, so `.app-layout .who`'s own `color: var(--band-muted)` leaked into a completely unrelated component nested under it; renamed the register's own one to `.what` and added an explicit `color: var(--ink)` on its own `b`, and `scripts/screenshot-demo.ts` now asserts >= 4.5:1 there in both themes, the same way it already asserts no horizontal overflow. The Accounts screen's own phone row gets a "Close" button beside the navigable name/balance (two sibling buttons, not one nested inside the other), a fixed 44px touch target that never wraps onto its own line. The register's own phone search field now sits on its own full-width row with a short "Search" placeholder, rather than being squeezed illegibly by "New transaction" next to it. Minor: the desktop table's "Date" column text was reading 6px further right than its own header — `.open-row`'s button never reset the browser's own default button padding, so its text sat inside that too, on top of the `<td>`'s own identical padding; and a docblock comment calling the phone/desktop choice "plain CSS, not a matchMedia check" was stale now that `usePhoneWidth()` makes that call in JavaScript.

`#331`, the phone layout for the budget month (design.md, "Budget month on the phone"). A fixed bottom tab bar (`AppLayout.tsx`) joins the band on every screen below 600px — Budget, Accounts, More (workspace settings); Portfolio and "a central button for quick expense entry" are both left out, no screen yet, the latter tracked on its own (`#367`) rather than wired to a stand-in. The budget month itself, on a phone: a compact timeline (`Timeline.tsx`'s new `compact` prop, `computeTimeline({ compact: true })` — the marks/labels themselves were already there, `#326`'s own "keeps only the marks, 'today' and the income still to come" rule), the "To do" list capped to three items with "+N more" (`Todo.tsx`'s new `limit`), full-width bars (already built by `#324`'s own media query), and the whole group header — chevron, name, overspent badge — now one button rather than just the small chevron icon, so "Groups collapse by tapping their name" holds (a side effect every width gets, not a phone-only change, since the wider click target does no harm on the desktop either). Tapping a category or a to-do item replaces the whole screen with that category's own detail instead of opening it inline under the row — the same `RowDetail`/`PaymentCategoryDetail` content either way, `DetailFrame.tsx` (new) only swapping "× Close" for a "← Budget" back link; a to-do item naming several targets at once opens the "Targets" panel instead, since it has no one category of its own, and `Todo.tsx`'s own `onItemClick` is opt-in, so the desktop stays exactly as non-interactive as `#326`'s own docblock already said. "Assign" and "Move money" stay the existing `SideSheet`-based forms — already close enough to full screen on a real phone (`max-width: 100vw`) that a second, distinct full-screen mechanism was not worth building for them.

`#337`, the timeline and "To do" list on the account register (design.md, "Account register"). The same `Timeline.tsx`/`computeTimeline` the budget month uses, fed this account's own events (`useAccountRegister.ts`'s new `month` parameter, `GET .../budget-months/:month/events?accountId=`, already account-filterable since `#325`/`#346` — no API change needed). A new, separate "To do" list (`RegisterTodo.tsx`/`registerTodo.ts`), not `@envelope/core`'s own `computeTodos` (a different list: Record/Mark/Reconcile, not Open/Fund): **Record** an overdue scheduled transaction is a direct one-click action calling `POST .../scheduled-transactions/:id/record`, exactly like `ScheduledPanel.tsx`'s own already-shipped button — *not* the mockup's own pre-filled form, since that endpoint takes no override fields at all (always the scheduled transaction's own stored values), and a form the user could edit, then silently discarded on submit, would be a worse bug than skipping the review step; **Mark** a pending transaction reuses the existing `updateTransaction` call the per-row toggle already makes; **Reconcile** stays informational only, appearing once something is cleared, the same way every `Todo.tsx` item was before it had a destination — the reconciliation flow itself is `#60`'s own job. `@envelope/core`'s new `computeProjectedBalance` (today's balance plus this month's not-yet-recorded scheduled items, already in the same events fetch) renders in the header's own facts row, next to Cleared/Pending. The timeline and "To do" list fold away entirely while a side sheet is open (`.over`'s own conditional render, not a CSS visibility toggle) — and never show at all on the phone, where the "To do" list's own first two items sit directly under the balance instead, no timeline, matching design.md precisely. `daysInMonth`/`monthLabel`/`todayOf`/`toTimelineEvents` moved out of `BudgetScreen.tsx` into the new `monthEvents.ts`, shared by both screens rather than duplicated.

`#62`, the Italian translation catalog (ADR 0004: "Italian... must always be complete"; ADR 0009: FormatJS). A new workspace package, `packages/i18n` — `locales/en.json` is generated from the source's own `defaultMessage`s (`apps/web`'s new `pnpm i18n:extract`, `@formatjs/cli extract` with a small custom formatter flattening its own `{id: {defaultMessage}}` output to the plain `{id: string}` shape the catalog actually is), `locales/it.json` is hand-translated against it, leaning on the mockups' own Italian sample data for terminology already established there (`docs/ux/mockups/*.html`) rather than inventing fresh wording. `checkComplete.ts`'s own test compares every key between the two (missing, or stale — present in Italian but no longer in English) *and* every ICU argument each message uses, however deep inside a plural or select it sits (`{name}`, a plural's own case content, …) — a translation that silently drops or renames one breaks at render time, the one thing a plain "same keys" check would still miss; wired into CI as its own named step (`packages/i18n - catalog completeness`), the same convention every other test kind already uses (ADR 0007). Two message descriptors `@formatjs/cli`'s own static analysis cannot extract — a dynamic `id`/`defaultMessage` chosen by a ternary (`BudgetScreen.tsx`'s own group expand/collapse) and one keyed by a template literal (`ScheduledPanel.tsx`'s own recurrence unit) — are rewritten as separate, literal `formatMessage` calls instead, the same "look up a stable key, whichever call site is reached" idiom every other message in the app already uses. `apps/web`'s own `main.tsx` picks the interface language from the browser's own ordered preferences (`negotiateLocale.ts`) rather than hard-coding English — there is no "your account" settings screen yet to store a real preference, so this is the whole of "locale negotiation" for now; English never passes its own `messages` catalog (relying on each component's own `defaultMessage` instead), so it can never silently drift out of sync with a generated copy the way a stale `en.json` could.

## Configuration

Copy `.env.example` to `.env`. Vite only exposes variables prefixed `VITE_` to client code.

| Variable | Default | Meaning |
| --- | --- | --- |
| `VITE_API_URL` | — (required) | Where `apps/api` runs, e.g. `http://127.0.0.1:3000` |
| `VITE_KEYCLOAK_ISSUER` | — (required) | The "envelope" realm's issuer URL, e.g. `http://127.0.0.1:8080/realms/envelope` (`scripts/keycloak/bootstrap.sh`) |
| `VITE_KEYCLOAK_CLIENT_ID` | — (required) | The realm's public, PKCE-only client (default `envelope-api`) — the same client `apps/api`'s own `KEYCLOAK_AUDIENCE` names |

The API's own CORS policy (`WEB_ORIGIN`, `apps/api/.env.example`) must allow this app's origin — `http://localhost:5173`, Vite's own dev server port, is already the default on both sides. The Keycloak client's `post.logout.redirect.uris` attribute must include this app's origin too (the bootstrap script sets it to `"+"`, the same as its redirect URIs), or sign-out fails.

## Design

Screens follow [`docs/design.md`, "User interface"](../../docs/design.md#user-interface) and [`docs/ux/README.md`](../../docs/ux/README.md) (screen inventory, navigation, component catalog, accessibility baseline); a screen without a mockup in `docs/ux/mockups/` is not built from scratch (`CLAUDE.md`). The colour tokens in `src/index.css` are copied verbatim from the mockups' own `:root`; no other colours, fonts, shadows or card styles. Text is self-hosted, not loaded from Google Fonts (unlike the mockups themselves): Bricolage Grotesque Variable for display type (`--display`, narrowed via its `wdth` axis for titles and big figures) and Figtree Variable for body text (`--font`), both `@fontsource-variable/*` packages, both SIL OFL 1.1 — exact versions and upstream attribution in [`THIRD-PARTY-NOTICES.md`](../../THIRD-PARTY-NOTICES.md), copied as a static file into `public/` so it ships with every build. `vite-plugin-pwa`'s `workbox.globPatterns` includes `woff2` (and `md`, for that same file) so the installed PWA has them offline too.

## Current limitations

`e2e/sign-in.spec.ts`, `e2e/workspaces.spec.ts`, `e2e/accounts.spec.ts`, `e2e/categories.spec.ts`, `e2e/budget.spec.ts`, `e2e/transactions.spec.ts` and `e2e/targets.spec.ts` cover sign-in, sign-out, the workspace switcher, accounts, categories, the budget month, the account register and targets/quick assign end to end; the first caught `#308` (the Keycloak client's `webOrigins` silently breaking the token exchange's CORS in every real browser), `e2e/accounts.spec.ts` caught `#315` (`@fastify/cors`'s own default `methods` is `GET,HEAD,POST`, not every verb the API uses, so closing an account — the first PATCH call this app makes — failed silently in a real browser while every mocked unit test and `.inject()`-based integration test stayed green) — fixed in `apps/api/src/app.ts`. Not wired into CI yet (`e2e/README.md`): `#63`'s own end-to-end coverage grows from here as later screens land.

The band (`#323`) does not yet draw the mockup's second row of month-specific content (month navigation, "Unassigned") — `BudgetScreen` still renders that itself, inline, until `#324` gives it somewhere to live in the band. Below ~600px the band wraps onto extra lines instead of overflowing horizontally, but it is still the same desktop layout shrunk down, not the mockup's own dedicated phone design (bottom tab bar, separate markup) — that is `#331`'s job; the account register's own phone layout (`#333`) does not touch the band itself. `docs/ux/mockups/account-register.html`'s own desktop view still draws the sidebar account list `#323` retired in favor of the standalone Accounts screen — left un-redrawn, a known divergence between that mockup and the shipped layout, rather than rebuilding an eliminated pattern to match it. The "+ Add account" form has no dedicated mockup — composed instead from the onboarding's first-account step and the workspace-settings account list (`docs/ux/mockups/settings-first-run.html`), the closest existing patterns, rather than a new one invented for this screen alone. The categories screen has the same gap: no mockup draws "list, create, archive, reorder" as its own screen, so it is composed from that same mockup's "Categories" settings tab; a newly added group or category cannot be renamed afterward (`apps/api` has no rename endpoint), and archiving either has no undo. The account register has no payee autocomplete or "last used category" hint, and no live preview of a category's available amount before/after saving, unlike the mockup — both are nice-to-haves the issue's own scope ("Splits, transfers") does not ask for; a transfer's row shows "Transfer" without naming the destination account, since resolving it would need fetching every other account's own transaction list too. Quick assign has no live preview either, and only five of the mockup's six modes — "cover the scheduled transactions" has no endpoint yet. The budget month screen is still not fully interactive — every row, ordinary or a card's own payment category, opens to edit its assigned amount and move money, or to see and cover the card's debt (`#327`–`#329`), a category row shows its own reservation-clock status line when it has one (`#217`), "Scheduled" records and skips reservations (`#330`), and the band's own facts row shows days of buffer (`#344`), but a category's own target-meter status line is still its own later work. A card's own debt-source sentence is generic rather than naming the starting balance or the specific overspent categories, since the budget-month API does not yet attribute credit overspending to a specific card (`#355`). A scheduled transaction is always a single-category expense — scheduled income has no backend support yet (`#347`). The sign-in screen's own error state shows the generic `signIn.error.generic` message plus the raw, untranslated `Error.message` from `oidc-client-ts` as its technical detail — deliberately simpler than `docs/ux/mockups/sign-in.html`'s illustrative `invalid_state` example, since the library does not expose a small, stable set of error codes to translate individually (`docs/ux/README.md` updated to match). The PWA manifest uses a single SVG icon; proper multi-resolution icons are a visual-design follow-up, not a blocker for an installable shell.
